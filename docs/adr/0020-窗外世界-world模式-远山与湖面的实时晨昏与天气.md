# ADR-0020：窗外世界（world 模式）——远山与湖面的实时晨昏与天气

- 日期：2026-09-21
- 状态：已落地（机器侧全绿：typecheck / build / 438 单测 / 214 e2e），**待作者本地观感验收**
- 相关：ADR-0004（机器叙事）、ADR-0005（单强调色与 4px 网格为本站自有约束）、ADR-0015（铁律阈值化）、ADR-0016（/lab 图册）、ADR-0017（首屏打字机）、`docs/specs/line-hierarchy.md`、`docs/specs/bgfx-acceptance-matrix.md`

## 背景 / 问题

BgFx 的 canvas 背景从 v1 起就是「机器叙事」：网格底纹 + 走线级联 + 信号包 + 扫描线。
它证明了这个站是一台**通电的机器**，但机器永远在同一个时刻、同一种天气里运转——
访客看到的每一帧都一样，站点没有「此刻」。

作者 2026-09-21 提出两条硬需求：

1. 首页要「一眼惊艳」——足够多的动画 + 精美质量；
2. **要有时刻感**：白天/黄昏/夜晚要真的不一样，下雨要下雨、下雪要下雪。

并且明确授权：可破坏现有资产，推倒重来都行，「最惊艳」优先。

## 决策

### 一、世界住在 canvas 里，不新增 DOM 装饰层

视觉铁律（ADR-0015）规定全站常驻装饰层 ≤2 层，而网格 + 扫描线已经顶格。
因此「窗外」**全部画进现有的 `#bgfx-canvas`**，不新增任何 DOM 背景层。
唯一的例外是 scrim（`.bgfx-scrim`）——它本来就在装饰栈里（层序见 `line-hierarchy.md` §四之一）。

### 二、一个主驱动量：太阳高度角（sunAlt）

**画面的一切都是 sunAlt 的连续函数**，不是钟点、不是「模式」：

| 由 sunAlt 决定 | 怎么决定 |
|---|---|
| 天空 6 条色带 | 8 个关键帧之间逐色插值（`sampleSky`） |
| 天体（太阳/月亮）位置与是否可见 | 日出日落锚点算水平弧位 `arcX`，高度 = `sin(arcX·π)` |
| 星星亮度 | `starlightFor(alt)` |
| 山色（远山/近山两档） | 关键帧里的 `ridgeFar` / `ridgeNear` |
| 窗灯/湖面波光 | 随 starlight 淡入 |
| 首访「点亮仪式」 | 退化为**一次 sunAlt 从 -0.55 到真实值的插值** |

为什么是太阳高度而不是钟点：真实世界的晨昏本就由太阳高度决定。
冬天 17:40 的黄昏与夏天 19:00 的黄昏**自动各自正确**，不需要按月份查表。

### 三、真的有窗（2026-09-21 二次返工）

第一版只有一片铺满视口的风景。作者当天看图后连提三条，全部成立：

> 「所为的窗不对，没有窗，哪来的窗，我没看见窗」
> 「`#hero > div:nth-child(1)` 遮挡了窗外的景色，你截图没看到吗」
> 「底部的灰色的框是什么？」

三条各自对应一个真实缺陷：

| 症状 | 根因 | 修法 |
|---|---|---|
| **没有窗** | 风景铺满视口 = **壁纸**，不是窗外。缺一个前景框把景色框住、把边缘遮掉 | 新增 `windowSpec()`：景色裁进窗洞（`ctx.clip()`），窗洞之外画框。**只做外框 + 窗台，不做中竖梃**（竖向分格把开阔的景切碎） |
| **面板挡住景色** | 山脊原本落在 `0.56h–0.66h`，正被 hero 面板（`0.32h–0.71h`）压住 → 中央的山全被吃掉、只剩左右两条边 | 地平线压到 **0.80h**、山脊压到 0.70h 以下 → 远山近山 + 湖面整条带落在面板**下方**，全宽可见；面板上方留给天空、云、日月 |
| **底部灰框** | 是 `.bgfx-scrim` 的顶边：CSS 写死 `top: 100vh`，但 nav 是 sticky 占 60px 流、hero 因此从文档 y=60 起，翻页脚本又把 hero 顶对齐到视口 0 → scrim 切在 hero 底部**上方 navH** 处，在首屏底部留下一道 72% 暗玻璃的硬边 | scrim 顶边改为**实测 hero 底边**（BgFx 每帧本来就在量 hero 的 rect）。nav 高度随断点变（桌面 60 / 窄屏 94），常数一定错 |

**框的三档剖面**：第一版只画了一圈暗边，读作 letterbox 而不是窗。现为
外缘阴影 → 框面 → **内缘受光**（天光打在窗洞侧壁）三档；窗台同理：受光台面 → 台沿 → 台体。
框取 `--gb-*`（换主题就换框），景色不取——**这一圈就是「窗外实景固定 / 窗内主题随身」的分界线**。

> **增量（2026-09-22）**：作者反馈「第一眼不觉得是窗，只有形状，没有窗户的元素」。
> 上表「不做中竖梃」的裁决对象是**全高中梃**（切碎开阔景 + 被 hero 面板挡住）；
> 本轮改为**横梃（0.52h，主景带上方）+ 上扇短竖梃**，主景带（太阳与山）仍不分格。
> 同时补齐三件窗户元素：①框面对比拉高（bg+16% → bg–text 中点偏 text，原值在亮色
> 房间几乎隐形）；②两道斜向玻璃高光带（阶梯矩形，像素语言里的斜线就是楼梯）；
> ③窗台顶缘 2px accent 受光带（与全站「面板顶缘 = 2px accent」同语言）。
> 已知取舍：clear 白天 + dark 房间时，中灰框面与亮蓝天带的**亮度**可能撞车
> （实测亮度差仅 3.3）但颜色明不同——e2e 判据因此量逐通道色差而非亮度
> （`tests/e2e/world.spec.ts` 窗棂用例）

### 四、场景 = 远山与湖面（作者 2026-09-21 定稿 A 案）

初版做的是**城市天际线**（珠江两岸 + 广州塔 + 楼群窗灯）。作者看图后否决：

> 「我并不喜欢窗外是城市，太压抑了」

根因是构成而不是细节：竖线 + 暗块 + 密集窗格天然压迫，楼群还把画面下半部封死，
吃掉了天空的呼吸感。改案为**远山与湖面**：

```
天空（约 0.7 屏高）
　远山脊线 0.775h ± 0.06h  ← 最淡，几乎融进天空（大气透视）
　近山脊线 0.795h ± 0.03h  ← 更暗更实，与远山错开才有纵深
湖面线 0.80h
　湖面：逐行镜像天空色（越近越暗）+ 静态波纹剪切 + 水平反光条纹
　山影倒影：镜像叠加（远山 0.12 / 近山 0.20）
　芦苇：左右各 2 丛前景剪影，随风轻摆（画面中央 60% 留空）
```

山脊线用**三角波**叠加（`|2·frac−1|`）而不是正弦：正弦叠加出来的永远是平缓的包，
看着像沙丘/波浪；三角波才有峰尖谷圆——这是「山」而不是「沙丘」的关键。

### 五、世界只住首屏

canvas 透明底，天空随滚动淡出：`worldAlpha` 由 `#hero` 的 rect 可见度算出，
离开首屏回到主题底色的「房间」。**雨雪粒子全站飘**（阅读页也下——那是窗外，
不是首屏的布景），scrim 区有亮度补偿。

### 六、天气以作者城市为准，不弹定位授权

天气/时刻一律以**作者所在城市**（广州，`src/lib/config.ts` 的 `siteWeather`）为准，
全世界访客看到的都是「作者窗外」。这样零授权弹窗、零隐私成本。

- 数据源：Open-Meteo 免费无 key；
- `localStorage` 缓存 30 分钟（键 `8bitme:weather`）；
- **失败静默降级为晴**（页面永远有合理画面）；
- 这是主站**第一个也是唯一一个**运行时外部请求。

e2e 一律 mock Open-Meteo（`tests/e2e/helpers/mock-weather.ts`）：
离线可跑，且避免网络 resource error 毒化「控制台零报错」断言。

### 七、天空用固定实景调色板，不参与 13 套主题

13 套主题是**窗内的机器世界**（GB 四色）；窗外是**实景**，不跟着主题变。
所以 `sky-palette.ts` 是独立数据源，与 `themes.ts` 无耦合。

## 三档模式

`MODES = ['off', 'world', 'core']`，`DEFAULT_MODE = 'world'`：

| 档 | 画面 |
|---|---|
| `world`（默认） | 窗外世界 + 天气 + 晨昏 |
| `core` | 原 v1–v4 的机器叙事（网格/走线/信号包/扫描线），无天空 |
| `off` | 纯主题底色 |

旧档（`stars` / `rain` / `scan` / `wave` / `grid`）由 `normalize()` 归一到 `world`。

## 视觉铁律三问（开发流程文档 要求的自我否定框架）

1. **装饰层是否在预算内？** 是。没有新增 DOM 装饰层——世界全画在既有的 `-3` 层 canvas 里，
   层数仍是网格 + 扫描线 2 层。天空是 canvas 内容，不是 CSS 背景层。
2. **移除装饰层后 UI 是否仍有结构感？** 是。世界是**背景风景**，不承载分隔/引导/位置/状态语义；
   面板、导航、按钮的描边与层级全部来自主题色与既有结构线。
3. **UI 元素是否独立表意？** 是。世界不参与任何 UI 语义；`hero-live` 读数行的信息
   （LOCAL 时刻 / 城市 / 天气词）由文字承载，不依赖天空颜色。

## 慢道登记（新增线元素）

命中慢道条件（新增线元素）→ 已在 `docs/specs/line-hierarchy.md` §六登记：

| 线元素 | 功能 | 规格 |
|---|---|---|
| **窗框**（外缘阴影 / 框面 / 内缘受光） | 让「窗外」成立（没有它，风景只是壁纸） | 18px 三档，取 `--gb-*` 主题色 |
| **窗台**（受光台面 / 台沿 / 台体） | 窗的下沿 + 盖住底部的水 | 54px 三档 |
| 山脊受光边 | 天光勾出山形（没有它山体是一块死色） | 1px，山体色向天空底带混 34% |
| 水岸线 | 山脚与湖面的分界 | 2px，近山色压暗 35% |
| 湖面反光条纹 | 水面质感（像素水面的标志） | 1–2px，行距 7px，透明度 0.16 |
| 涟漪 | 雨落湖面 | 1px 横线，宽度随寿命 4→20px 扩散 |
| 芦苇杆 | 前景剪影，随风轻摆 | 1–2px，穗 4×5px |
| 积雪边 | 雪天最强视觉信号 | 正弦厚度 0–11px，远山 35% / 近山 100% |

全部为**底纹档**（不承载分隔/引导/位置/状态语义），不进结构线白名单。

## 走过的假绿坑（写进 ADR，防再犯）

`world.spec.ts` 的「山脊轮廓」断言迭代了 **4 版**才真正有效，每一版都是绿的但都是假的：

| 版本 | 判据 | 为什么假绿 |
|---|---|---|
| ① | 逐列找「比天空暗」的第一处 | 天空本身是 6 条**水平**色带，抓到的是色带边界（每列同高 → 起伏 0） |
| ② | 逐列找「蓝度 B−G 骤降」 | ①天空底带偏白、夜里近山与天空都是深蓝，颜色分不开；②扫描窗放到地平线以下会命中**山影倒影**（镜像的山形同样有起伏） |
| ③ | 只测「有相邻行亮度骤降」 | 近山脊线的**受光边**（亮线）到山体本身就是一次骤降——把近山画成天空色时它照样存在 |
| ④ | 只测「比上方天空暗」 | 天空纵向本就渐亮，`bands[2]` 比 `bands[4]` 暗 → 假绿 |

**最终有效判据**：把**山色本身**拿到画布上数像素（色值取自源码 `sampleSky(alt)` 这一唯一事实源），
且只扫 `y < horizonY - 4`（排除水面倒影与 2px 水岸线）。
四个反例全部验证过必红：近山→`bands[2]`、近山→`bands[3]`、近山→`ridgeFar`、山脊振幅→0。

另一条经验：**深夜的天空顶部色（`#05081a`）与近山色（`#070b1e`）只差 2–4/通道**，
会撞进色值匹配的容差里 → 该用例固定到正午（`addInitScript` 覆写 `Date`）。

### 同一类坑的第二次：「水面比天顶暗」

守水面的第一条判据是「底部（0.92h）比顶部（0.12h）暗」——**它随钟点翻脸**：
真实夜空本就**近地平线最亮**（湖面镜像是地平线色带），深夜的水面确实亮过天顶。
改成**与山脊相对取样**（找「两条脊线都最低」的那一列，取它上方 4px 作天空基准、
地平线下方 20px 作水面），判据就与钟点无关。反例（水面 = 天空原色、无暗化）已验证必红。

> 取样用 `min(farRidge, nearRidge)` 而不是 `max`：山体是「脊线 → 地平线」**填充**，
> 取 `max` 会把取样点落进远山体内部，量到的是山不是天空。

### 第三次：几何改动之后，测试里的硬编码窗口全成了假的

把地平线从 0.68h 压到 0.80h 之后，三条 e2e 立刻红——**不是代码坏了，是测试在量别的东西**：

| 写死的量 | 失效方式 |
|---|---|
| 山脊扫描窗 `0.5h..0.66h` | 山体整体下移 → 窗口落空 |
| 水面条纹窗 `0.75h..0.95h` | 0.75h 已经在地平线**以上**（是山），而且窗台那几行不是水 |
| `genScenery(1440, 900)` | 画布宽是 **1424**（竖滚动条吃掉 clientWidth）→ 取样列落到另一座山脊上 |
| `sc.farRidge[x][1]` | `ridgeLine` 按 `step = round(w/220) ≈ 6` 抽点，**数组下标不是 x 坐标** → 必须用 `ridgeAt(pts, x)` |
| 取样列 `x = 10` | 落在**窗框**里（框宽 18px）→ 三个取样点全是框体色，判据变成「框 == 框」 |

**规矩：测试里凡是与场景几何有关的量，一律从 `genScenery(画布真实尺寸)` 派生，
不许写比例常数；数组一律用 `ridgeAt()` 取，不许下标索引。**

### 云的三条反馈（2026-09-21）

> 「云运动的太突兀了，不够自然」「太快了，像是匀速行驶」「每朵云的形状像是固定的」

三条全部成立，且各有明确根因：

| 症状 | 根因 | 修法 |
|---|---|---|
| 太快 | 近层 `vx = 0.34 px/帧` = 26 px/s，读作贴纸在滑 | `CLOUD.SPEED_*` 降到 0.17 / 0.075 |
| 匀速 | `c.x += c.vx`，`vx` 恒定；滚动视差还是另一个匀速叠加 | `cloudGust(t, ph)`：**两个不同频率的正弦相乘**（单频正弦的加减速可预测，看一会儿就知道节奏），输出 0.30–1.20，每朵云相位不同 → 云与云之间也不同步 |
| 形状固定 | `blocks` 是 **4 块写死的比例模板**，所有云只是缩放不同 | ①生成期：凸起 2–4 个、位置大小全随机、侧翼随机存在；②运行期：`morphCloud()` 每块各自的低频**整数**伸缩（平滑缩放会产生抗锯齿灰边、破像素语言）+ `cloudBob()` 垂直起伏 |

**像素云的形状变化必须是整数伸缩**：这是像素语言与「缩放」的分界——整数伸缩天然是
「这块像素多了一行」，非整数缩放则产生抗锯齿灰边。

## 代价与未结

- 每帧多两次 offscreen 重绘（天空半分辨率 + 山湖全分辨率），只在 `dim`/`resize`/帧切换时重算；
- 雨雪粒子全站飘，`rainDropCount` 钳在 320、`snowFlakeCount` 钳在 190；
- reduced-motion：降频不冻结；点亮仪式跳过；**雷闪禁用**（WCAG 2.3.1）。
- 未结：白天太阳光晕在浅色主题下是否够亮、雨天云层与 CRT 扫描线叠加是否有摩尔纹，
  留给作者观感验收。

## 加密度：场景细节层（2026-09-23）

> 「窗外的景色太简单，太粗糙了，不够精美」

观测（截图评审）：两层山是**两块纯色剪影**、岸线是一条光秃直线、湖面大而空。
密度不足不是「再加一层山」（面板下缘 0.71h 只给山带留了 ~8%h 的空间，第三层山
要么撞面板要么与远山糊成一片），而是**缺细节层**。本轮加四件，全部纯函数进
`sky-scene.ts`，静态件画进 land 缓存帧（零每帧成本）：

| 元素 | 落点 | 守卫 |
|---|---|---|
| **山体皴纹**：近山脊线下 45% 采样点挂明/暗竖纹（受光面/背光面两色） | `hatchStrokes()` + land 帧 | unit：贴脊线、恒在地平线上、明暗两色都有 |
| **岸树 4–6 丛**：团冠剪影贴地平线（最小间距 9%w）；**小岛一座**载树，水面中景锚点 | `TreeCluster` / `Isle` | unit：结构 + 间距；e2e：树冠/滩涂色像素落在画布上（正午晴日，色值同源派生） |
| **渔舟**：两个慢正弦叠加的游移（不是匀速直线）+ 随波起伏；入夜船灯（`windowLit`，与窗灯同色）+ 水面光柱倒影 | `BOAT` / `boatPose()` | unit：整数位、恒在水面内、游移不重复；e2e：船道带内船体色密集暗块 |
| **晴日飞鸟**：3–5 只人字小队掠过面板上方天空带（y ≤ 0.30h，避开门面面板），阴雨天不出 | `BIRD` / `birdWingUp()` | unit：参数区间 + 扑翼两态；e2e：晴日出现且移动、雨天不出（debug 钩子 `flock`/`flockX`） |

**为什么飞鸟只在晴日**：`stepWorld` 调度闸 `fx.rain === 0 && fx.snow === 0`——
雨天鸟不飞是常识也是画面逻辑（阴雨世界已由 dimSky 统一压灰，再塞活物反而吵）。

**判据与被守者同源**：e2e 的树/岛/船色全部用 `sampleSky(alt).ridgeNear` 经与绘制层
相同参数的 `lerpHex` 复算（正午帧 + 晴天 dim=1），夜里近山与天空只差 2–4/通道、
阴雨 dim 又会整体压暗——所以这条测试必须 mock 正午 + 显式晴天 + 等 `bootP ≥ 1`。


## 倒影随波扭曲的柔化（2026-09-23 二轮）

> 「湖面倒影随波扭曲的柔化」

**旧病**：山影倒影是 land 缓存帧里画死的静态镜像（`translate + scale(-1)` 一次成像）
——一张「倒挂在水面上的照片」，纹丝不动，一眼假；岛的倒影也是一块恒定 alpha 的暗斑。

**改法**：倒影从缓存帧里**逐行动态采样**（`drawReflection()`，drawWorld 每帧执行）：

| 手段 | 参数（`REFLECT` 常量，单测守线） | 为什么 |
|---|---|---|
| 逐行镜像取样（2px 行） | `STEP = 2` | 1px 源行画进 2px 目标行 = 免费柔化 + drawImage 次数减半 |
| 每行正弦水平错位 | `SHEAR_Y / SHEAR_T / SHEAR_MAX = 3` | 随波扭曲：纵向波形连续、随时间流动；越近观察者错位越大（`0.3 + 0.7·depth`，远近平波） |
| 透明度纵深衰减 + 低频呼吸 | `ALPHA 0.3 / ALPHA_FLOOR 0.3` | 柔化的另一半：不再是一张恒定透明度的硬镜像 |
| 「破镜」行（alpha ×0.25） | `GAP_T` | 波浪把镜像打断的暗带随时间**向下流**——静水每隔几行断一次，才是水不是镜 |

- 山形仍来自 land 缓存帧，动态层只做采样与错位 → 零重新渲染；reduced-motion 下波速 ×0.35（降频不冻结）。
- **顺带修掉一个隐性 bug**：`fx-runtime.applySize()` 现在 `imageSmoothingEnabled = false`——
  canvas 尺寸重置会重置该状态，所以必须每次 resize 重设。此前 CSS `image-rendering: pixelated`
  只管**元素缩放**，管不到 `drawImage` 内部插值：半分辨率天空帧放大时一直在被双线性柔化，
  「半分辨率放大 = 免费像素化」的设计意图从未真正成立。
- 守卫：unit 5 条（确定性/整数/上限、纵深放大、透明度衰减+呼吸、破镜流动、参数哨兵）；
  e2e 1 条（避开活物取样的倒影带两次采样差 > 3000——扭曲/呼吸/破镜任一失效都红）。
- 船影同步改用同一套 `reflectShear` 语言（错位暗斑），与山影同源。

## 像素精化：1:1 天空 + 细山脊（2026-09-23 三轮）

> 「像素风本身太粗糙了 / 整个景色的像素不够精致」

**诊断**：画面粗糙的主源有两个——
1. **天空帧半分辨率放大**（`sw = w/2`，绘制时 ×2）：所有色带、拜耳抖动、云间过渡
   都是 **2×2 屏幕像素一格**。这是「整个天空像打了马赛克」的最大单点来源。
   （「半分辨率放大 = 免费像素化」的原始设计意图，在 ADR-0021 轮已确认从未真正成立——
   双线性插值一直在柔化它；上一轮关掉插值后，2×2 的块感反而完整暴露了出来。）
2. **山脊采样密度**（`ridgeLine` step = w/220）：台阶踏面 ~6.5px，1:1 天空下
   「楼梯齿太粗」非常显眼。

**改法**：
- 天空帧改 **1:1 全分辨率**渲染（色带 fillRect 与抖动 ImageData 都按全屏像素算），
  拜耳抖动变成 1px 棋盘格——带间过渡读作细腻的像素渐变而不是粗色块。
  代价只是天气/dim 变化时重建缓存的成本 ×4（仍是一次性，运行时零成本）。
- `ridgeLine` step = w/440（max 2px）：踏面 ~3px，山脊轮廓细腻一倍。
- 回归铁律不变：坐标仍全整数、确定性 rng、最近邻插值（无抗锯齿灰边）。

**测试教训（又一次「测试在量别的东西」）**：`ridgeLine` 尖峰单测在**索引空间**量
陡降（`pts[i±2]`），step 减半后 ±2 索引的水平窗从 ~14px 缩到 ~6px，陡降量跟着缩水
→ 假红。修法：改用 `ridgeAt()` 在 **x 空间**取 ±14px 固定窗，判据与采样密度解耦。

## 画法精化：连续渐变天空 / 排叠云 / 山体体积（2026-09-23 四轮）

> 「完全不够」——分辨率只是地基，画面读作粗糙是因为**画法**：色带内部是死平大色块、
> 云是大块拼板、山是纯色剪影贴到水边。这轮按像素画的画法重做：

| 对象 | 旧画法（粗糙根源） | 新画法 |
|---|---|---|
| 天空 | 6 条平色带 + 带间 24px 过渡区（带内死平） | **全高度连续拜耳渐变**：6 个带中心作锚点（锚点行纯带色），带与带之间整段 1px 拜耳棋盘混色——天空读作细腻的像素渐变 |
| 云 | 大块拼接（底座 40–160px 宽 + 顶部凸块），两档明暗，顶块会悬空 | **扫描线排叠**：3–7 排 2–4px 高横条，自底向上收窄 + 35% 排单侧鼓包，平底圆顶；三档明暗按「排底在云高中的位置」取色（低处受影、顶部受光） |
| 远山 | 纯色贴到水边 | 山脚 ~16px **大气透视坡**（逐行溶进天色，贴水最浓），只洗底部、山脊线附近保持纯色（countColor 窗口安全） |
| 近山 | 单受光边 + 稀疏皴纹 | 受光边下方 2px 再勾**暗棱双线**（像素山的体积）+ 确定性 **1px 两色碎点**（w·2.8% 密度，暗点受影/亮点受光，只洒在雾坡以上） |
| 山脚薄雾 | 单条 0.12 等宽硬带 | **逐行坡**（贴地平线最浓 0.16，向上淡出到 0.04）+ 水线下 3 行余雾 |
| 湖面 | — | 贴岸亮带：地平线以下 8 行逐行衰减的天色亮带（「最远处的镜面」反射最多天光） |

- 中途自己抓到的缺陷（2x 特写评审）：顶排碎凸悬空（小方块飘在底板上）→ 换排叠画法根治，
  并补 unit 守卫：**底排满宽平底 / 顶排窄于底排 / 每排 2–4px / 排排首尾相接**——
  防止未来再改回「等宽塔」或「脱节排」。
- 天空渐变成本：每帧缓存渲染多写 ~100 万像素 ImageData（天气/dim 变化时一次性），运行时零成本。

## 月相：阴晴圆缺（2026-09-21 作者提出）

> 「月有阴晴圆缺，不是所有时候都是圆的」

- **纯函数**（`sky-time.ts`，判据同源）：`moonPhase(nowMs)` 从真实时钟推相位
  （朔望月 29.5306 天，纪元 2000-01-06 新月；测试可用假时钟钉死）；
  `moonLitRow(dy, r, ph)` 给出月盘某行的**受光区间** [x0, x1)——
  明暗界线是与盘共弦的椭圆（半轴 c·cos(2πph)），盈月亮右、亏月亮左（北半球），
  满月全盘受光、新月受光 < 1px 不画。坐标全整数。
- **画法**：月亮不再 `pixelDisc` 满盘一张圆纸——逐行只画受光区；
  环形山逐像素判定落在受光区才画（亏损时随盘一起隐去）。
- **e2e**（世界契约）：钉假时钟 2026-09-21 23:30（盈凸月 ~78%），从同一套纯函数
  （moonPhase + moonLitRow + skyMoment + bodyPos 的屏幕映射）推出受光 bbox 的
  期望 x 区间，与画布上 moon 色实心段逐一比对——相位、方向、宽度全同源；
  光晕是稀疏抖动点、星点是 ≤3px 段，都不可能冒充月盘（段长 ≥ 4 过滤）。
- unit 15 条（相位周期性/纪元/值域 + 受光区几何：满/弦/娥眉/盈凸/对称/单调/整数）。

## 天气细分 + 玻璃雨 + 雷电 + 环境音（2026-09-22 作者四条反馈 + 声音追加）

> 「下雨的天空只有几片云，不合常理」「雷暴没有雷」「不同雨的天气下雨的样子应该不同」「雨应该打在窗户上，雨非常大甚至能流进窗户」+「雨/雷/风要有声音，风大窗户要振动」

- **云量分档**：`genClouds` cover ≥ 0.6（阴/雨/雪/雷）进密云档——云数 `11 + (cover−0.6)×30`（较原 3+12c 翻倍）、块宽 ×1.25、云带下沉（y 上限 0.44h→0.52h）。晴天档不变。
- **雨强分化**：`WeatherFx` 加 `wind`（drizzle 0.4 / rain 0.55 / thunder 0.85，e2e 可测）；`rainLook(强度)` 纯函数给雨丝「短慢直 vs 长快斜」三参数（lenMul/vyMul/slantK）——毛毛雨是垂直细痕，暴雨是斜长雨幕。
- **玻璃上的雨**：与穿过画面的雨粒子分两层——玻璃滑痕（1px 短痕缓滑，`glassStreakCount`）+ 暴雨沿窗流（2px 水股半透明，`glassStreamCount` 仅强度 ≥0.85）+ **窗台积水**（`sillWaterHeight`，雷暴档台面积水 3px 带 shimmer）。全部裁在窗洞内。
- **雷**：`genBolt` 像素闪电线（锯齿折线 ≤40 顶点，从云里劈到 0.8hy 山后），闪白 9 帧 + 折线压在闪白上；雷声与闪光同步（下条）。
- **窗户振动**：`windowShake(frame, wind)` —— wind ≥ 0.5 时窗框每 3.5s 颤一阵（±1..2px 确定性正弦簇），reduced-motion 不颤。
- **环境音（`src/lib/ambience.ts`，新）**：Web Audio 程序化合成，零音频文件。雨 = 带通噪声（强度调增益 0→0.13 与音色 1100→2600Hz）；风 = 320Hz 低频带通 + 0.07Hz 阵风 LFO；雷 = 110Hz 低通 rumble（主爆 + 两回声，`rumbleBursts` 纯函数）。**与画面同源**：只由 `{rain, wind}` 推参数。浏览器自动播放策略 → 首次手势后解锁；静音复用 `8bitme:sfx`（一次开关管全部声音）。
- 守卫：unit（云档/rainLook/玻璃雨三量/窗颤/genBolt/ambience 混音与 rumble 调度，全整数与确定性）+ e2e 三条（雷暴 bolt 像素真的在画布上、玻璃雨条数随雨强且坐标全落窗洞、风大窗颤出现过非零而晴天恒 0）。

## 雨/雷换真实录音（2026-09-22 作者裁决）

> 合成雨声三次迭代全被否：白噪感 → 2s 循环接缝爆点（「跟心跳一样，很有压力感」）→ 两级低通双链仍「太烦躁」。
> 作者问「为什么不考虑用真实雨声？复古的意义在哪？」——裁决如下。

- **设计口径**：像素复古的语言属于**视觉与 UI 音效**（方波 click、像素雨滴画法）；「窗外传来的环境声」是拟真物，不该用程序化噪声硬造。真实录音反而强化「这是一扇真窗户」。
- **雨**：`public/audio/rain-loop.mp3`（**CC0**，OpenGameArt「AMB Rain Loop 1」/ kresiek-the-furry，1.09MB / ~70s 循环）——`<audio loop>` 播放，音量随雨强映射（`rainLoopVolume`：毛毛雨 0.48 / 中雨 0.71 / 雷暴 0.9），30ms 步进平滑淡入淡出，加载失败静默禁用。合成雨链（低通白噪 + LFO 层）全部退役。
- **雷**：`public/audio/thunderclap.wav`（**CC-BY 3.0 © Jerimee, OpenGameArt**——署名在此与本模块头注释，勿删）。注意：原下载件扩展名 .ogg 但容器实为 RIFF/WAVE，**已诚实改名 .wav**（不赌浏览器嗅探）。闪先雷后（0.35–0.9s 随机延迟，物理正确）；资产加载失败自动回退合成 rumble（保留为降级路径）。雷暴天气到位即预缓冲，别让第一声雷迟到。
- **首闪时机**：切到雷暴 / 重新播种后 **~1.5s 必闪第一道**（原 9–16s 平均间隔让人「切过来看不到雷」——作者实抓），后续保持 9–16s 常态节奏。
- **风声仍合成**（低频带通 + 阵风 LFO）——风是持续环境层，合成成立且作者未否。
- 三个音频资产共 ~2.4MB，全部懒加载（手势解锁后才拉），不影响首屏。
- e2e 教训：闪白窗 ~300ms，node 侧轮询会与窗口赛跑假红——必须页内 rAF 逐帧锁存（实抓）。

## 雷声素材再换 + 雷随机化 + 雷雨配合 + 闪电柔化（2026-09-23 作者三条反馈）

> 「雷声怎么跟钟声一样，很怪」（前轮）→ 换 Mixkit 素材；「雷声像是循环播放，不够随机，随机事件，随机强度，应当和雨声节奏互相配合」「闪电不要太闪，对看的人的眼睛不太友好」

- **雷声素材**：Jerimee thunderclap（音色像钟声，否决）→ InspectorJ OGA 件（OGA 限速拉不完，弃）→ **`public/audio/thunder-strike.mp3`（Mixkit「Mid strength single thunder」，10s 真实单发雷击，Mixkit License 免费商用无需署名——注释仍留来源致谢）**。旧两任素材已删除。
- **闪先雷后升级为距离分层**（物理修正，作者：「看见闪电不应该是立马就有雷声」）：`thunderStrike(rng)` 每击抽签——**近雷 70%**（延迟 0.5–1.2s，响）/ **远雷 30%**（2–3.5s 才滚过来，闷而轻）。
- **雷随机化（「像是循环播放」的三味药）**：
  1. **簇式调度**（`nextThunderStrike` 替匀速 `nextLightning`）：每击 35% 概率在 1.8–5s 内再来一道（最多连 3 击），否则常规间隔 3.5–16.5s 且平方分布（短间隔多、长间隔偶发）——真实雷暴是「一串一串」的，不是节拍器；
  2. **随机强度**：每击音量 ±15% 抖动；
  3. **变调**：每击 playbackRate 0.85–1.15——同一份录音每次音高微差，直接杀死「同一段从头循环」的听感。
- **声画同签**：闪的强度与雷的延迟/音量/变调来自**同一次抽签**（BgFx 抽签 → `thunderRumble(strike)` 传同一签）——近雷亮闪快响、远雷弱闪闷雷迟到，视听同源。
- **雷与雨声节奏配合**（阵性涌动）：雷声真正出声的那一刻，雨声目标乘 `(1 + 0.18 × rainSurgeFactor)`——0.8s 快涌、5.2s 慢退（雷临头雨急、过后稍歇）；雨 loop 本身恒定，涌动乘在 `rainLoopVolume` 基准上。
- **闪电柔化**（作者：「对看的人的眼睛不太友好」）：全屏纯白瞬罩（`#e8ecf5` 0.42 均匀）→ **暖白渐变罩**（`rgba(255,243,220,…)`：天顶 α=0.5×peak → 地平线 38% → 水面 20% 渐灭，云层透光感而非相机闪光灯）+ **平方缓出**（`p²`：前快后慢软尾）；远雷闪强度 ×0.55。总窗长 9 帧不变，≤3 闪/s 合规口径不动；bolt 折线本体不变。
- 守卫：unit（nextThunderStrike 簇概率/区间/上限/平方分布；thunderStrike near/rate/抖动域；rainSurgeFactor 快升慢退包络 + applyRain 接线契约；BgFx 声画同签与渐变罩源码契约）——534 条全绿。

## 雷声素材池：四段实地雷击轮换（2026-09-23 作者第二次反馈：「依然奇怪、依然像循环」）

> 调研结论：上一任 Mixkit 素材是 **cinematic 设计音效**（合成/加工出来卖场面的，不是实地录音）——「听感不对」的根。而「依然像循环」的根是**只有一份素材**：雷是宽频噪声，±15% 变调人耳几乎察觉不到，抖动/变调都救不了「每次都是同一段波形」这件事。

- **治本方案 = 换录音**：`THUNDER_SOURCES` 四段**不同的实地雷击**，每击随机选一段且**不与上一段重复**（`pickThunderIndex` 纯函数）——连击天然换段，两道真雷还能叠着滚（真实雷暴如此），同段硬切尾音的问题也顺带消失：
  1. `thunder-close-rain.mp3` = InspectorJ「Thunder, Very Close, Rain, A」freesound #360328（**CC-BY 4.0，署名在 ambience.ts 模块头，勿删**）
