# ADR-0020：窗外世界（world 模式）——远山与湖面的实时晨昏与天气

- 日期：2026-09-21
- 状态：已落地（机器侧全绿：typecheck / build / 438 单测 / 214 e2e），**待作者本地观感验收**
- 相关：ADR-0004（机器叙事）、ADR-0005（单强调色与 4px 网格为本站自有约束）、ADR-0015（铁律阈值化）、ADR-0016（/lab 图册）、ADR-0017（首屏打字机）、`docs/specs/line-hierarchy.md`、`docs/specs/bgfx-acceptance-matrix.md`

## 背景 / 问题

BgFx 的 canvas 背景从 v1 起就是「机器叙事」：网格底纹 + 走线级联 + 信号包 + 扫描线。
它证明了这个站是一台**通电的机器**，但机器永远在同一个时刻、同一种天气里运转——
访客看到的每一帧都一样，站点没有「此刻」。

作者 2026-09-21 提出两条硬需求：

1. 首页要「一眼惊艳」——足够多的动画 + 精美质量；
2. **要有时刻感**：白天/黄昏/夜晚要真的不一样，下雨要下雨、下雪要下雪。

并且明确授权：可破坏现有资产，推倒重来都行，「最惊艳」优先。

## 决策

### 一、世界住在 canvas 里，不新增 DOM 装饰层

视觉铁律（ADR-0015）规定全站常驻装饰层 ≤2 层，而网格 + 扫描线已经顶格。
因此「窗外」**全部画进现有的 `#bgfx-canvas`**，不新增任何 DOM 背景层。
唯一的例外是 scrim（`.bgfx-scrim`）——它本来就在装饰栈里（层序见 `line-hierarchy.md` §四之一）。

### 二、一个主驱动量：太阳高度角（sunAlt）

**画面的一切都是 sunAlt 的连续函数**，不是钟点、不是「模式」：

| 由 sunAlt 决定 | 怎么决定 |
|---|---|
| 天空 6 条色带 | 8 个关键帧之间逐色插值（`sampleSky`） |
| 天体（太阳/月亮）位置与是否可见 | 日出日落锚点算水平弧位 `arcX`，高度 = `sin(arcX·π)` |
| 星星亮度 | `starlightFor(alt)` |
| 山色（远山/近山两档） | 关键帧里的 `ridgeFar` / `ridgeNear` |
| 窗灯/湖面波光 | 随 starlight 淡入 |
| 首访「点亮仪式」 | 退化为**一次 sunAlt 从 -0.55 到真实值的插值** |

为什么是太阳高度而不是钟点：真实世界的晨昏本就由太阳高度决定。
冬天 17:40 的黄昏与夏天 19:00 的黄昏**自动各自正确**，不需要按月份查表。

### 三、真的有窗（2026-09-21 二次返工）

第一版只有一片铺满视口的风景。作者当天看图后连提三条，全部成立：

> 「所为的窗不对，没有窗，哪来的窗，我没看见窗」
> 「`#hero > div:nth-child(1)` 遮挡了窗外的景色，你截图没看到吗」
> 「底部的灰色的框是什么？」

三条各自对应一个真实缺陷：

| 症状 | 根因 | 修法 |
|---|---|---|
| **没有窗** | 风景铺满视口 = **壁纸**，不是窗外。缺一个前景框把景色框住、把边缘遮掉 | 新增 `windowSpec()`：景色裁进窗洞（`ctx.clip()`），窗洞之外画框。**只做外框 + 窗台，不做中竖梃**（竖向分格把开阔的景切碎） |
| **面板挡住景色** | 山脊原本落在 `0.56h–0.66h`，正被 hero 面板（`0.32h–0.71h`）压住 → 中央的山全被吃掉、只剩左右两条边 | 地平线压到 **0.80h**、山脊压到 0.70h 以下 → 远山近山 + 湖面整条带落在面板**下方**，全宽可见；面板上方留给天空、云、日月 |
| **底部灰框** | 是 `.bgfx-scrim` 的顶边：CSS 写死 `top: 100vh`，但 nav 是 sticky 占 60px 流、hero 因此从文档 y=60 起，翻页脚本又把 hero 顶对齐到视口 0 → scrim 切在 hero 底部**上方 navH** 处，在首屏底部留下一道 72% 暗玻璃的硬边 | scrim 顶边改为**实测 hero 底边**（BgFx 每帧本来就在量 hero 的 rect）。nav 高度随断点变（桌面 60 / 窄屏 94），常数一定错 |

**框的三档剖面**：第一版只画了一圈暗边，读作 letterbox 而不是窗。现为
外缘阴影 → 框面 → **内缘受光**（天光打在窗洞侧壁）三档；窗台同理：受光台面 → 台沿 → 台体。
框取 `--gb-*`（换主题就换框），景色不取——**这一圈就是「窗外实景固定 / 窗内主题随身」的分界线**。

> **增量（2026-09-22）**：作者反馈「第一眼不觉得是窗，只有形状，没有窗户的元素」。
> 上表「不做中竖梃」的裁决对象是**全高中梃**（切碎开阔景 + 被 hero 面板挡住）；
> 本轮改为**横梃（0.52h，主景带上方）+ 上扇短竖梃**，主景带（太阳与山）仍不分格。
> 同时补齐三件窗户元素：①框面对比拉高（bg+16% → bg–text 中点偏 text，原值在亮色
> 房间几乎隐形）；②两道斜向玻璃高光带（阶梯矩形，像素语言里的斜线就是楼梯）；
> ③窗台顶缘 2px accent 受光带（与全站「面板顶缘 = 2px accent」同语言）。
> 已知取舍：clear 白天 + dark 房间时，中灰框面与亮蓝天带的**亮度**可能撞车
> （实测亮度差仅 3.3）但颜色明不同——e2e 判据因此量逐通道色差而非亮度
> （`tests/e2e/world.spec.ts` 窗棂用例）

### 四、场景 = 远山与湖面（作者 2026-09-21 定稿 A 案）

初版做的是**城市天际线**（珠江两岸 + 广州塔 + 楼群窗灯）。作者看图后否决：

> 「我并不喜欢窗外是城市，太压抑了」

根因是构成而不是细节：竖线 + 暗块 + 密集窗格天然压迫，楼群还把画面下半部封死，
吃掉了天空的呼吸感。改案为**远山与湖面**：

```
天空（约 0.7 屏高）
　远山脊线 0.775h ± 0.06h  ← 最淡，几乎融进天空（大气透视）
　近山脊线 0.795h ± 0.03h  ← 更暗更实，与远山错开才有纵深
湖面线 0.80h
　湖面：逐行镜像天空色（越近越暗）+ 静态波纹剪切 + 水平反光条纹
　山影倒影：镜像叠加（远山 0.12 / 近山 0.20）
　芦苇：左右各 2 丛前景剪影，随风轻摆（画面中央 60% 留空）
```

山脊线用**三角波**叠加（`|2·frac−1|`）而不是正弦：正弦叠加出来的永远是平缓的包，
看着像沙丘/波浪；三角波才有峰尖谷圆——这是「山」而不是「沙丘」的关键。

### 五、世界只住首屏

canvas 透明底，天空随滚动淡出：`worldAlpha` 由 `#hero` 的 rect 可见度算出，
离开首屏回到主题底色的「房间」。**雨雪粒子全站飘**（阅读页也下——那是窗外，
不是首屏的布景），scrim 区有亮度补偿。

### 六、天气以作者城市为准，不弹定位授权

天气/时刻一律以**作者所在城市**（广州，`src/lib/config.ts` 的 `siteWeather`）为准，
全世界访客看到的都是「作者窗外」。这样零授权弹窗、零隐私成本。

- 数据源：Open-Meteo 免费无 key；
- `localStorage` 缓存 30 分钟（键 `8bitme:weather`）；
- **失败静默降级为晴**（页面永远有合理画面）；
- 这是主站**第一个也是唯一一个**运行时外部请求。

e2e 一律 mock Open-Meteo（`tests/e2e/helpers/mock-weather.ts`）：
离线可跑，且避免网络 resource error 毒化「控制台零报错」断言。

### 七、天空用固定实景调色板，不参与 13 套主题

13 套主题是**窗内的机器世界**（GB 四色）；窗外是**实景**，不跟着主题变。
所以 `sky-palette.ts` 是独立数据源，与 `themes.ts` 无耦合。

## 三档模式

`MODES = ['off', 'world', 'core']`，`DEFAULT_MODE = 'world'`：

| 档 | 画面 |
|---|---|
| `world`（默认） | 窗外世界 + 天气 + 晨昏 |
| `core` | 原 v1–v4 的机器叙事（网格/走线/信号包/扫描线），无天空 |
| `off` | 纯主题底色 |

旧档（`stars` / `rain` / `scan` / `wave` / `grid`）由 `normalize()` 归一到 `world`。

## 视觉铁律三问（开发流程文档 要求的自我否定框架）

1. **装饰层是否在预算内？** 是。没有新增 DOM 装饰层——世界全画在既有的 `-3` 层 canvas 里，
   层数仍是网格 + 扫描线 2 层。天空是 canvas 内容，不是 CSS 背景层。
2. **移除装饰层后 UI 是否仍有结构感？** 是。世界是**背景风景**，不承载分隔/引导/位置/状态语义；
   面板、导航、按钮的描边与层级全部来自主题色与既有结构线。
3. **UI 元素是否独立表意？** 是。世界不参与任何 UI 语义；`hero-live` 读数行的信息
   （LOCAL 时刻 / 城市 / 天气词）由文字承载，不依赖天空颜色。

## 慢道登记（新增线元素）

命中慢道条件（新增线元素）→ 已在 `docs/specs/line-hierarchy.md` §六登记：

| 线元素 | 功能 | 规格 |
|---|---|---|
| **窗框**（外缘阴影 / 框面 / 内缘受光） | 让「窗外」成立（没有它，风景只是壁纸） | 18px 三档，取 `--gb-*` 主题色 |
| **窗台**（受光台面 / 台沿 / 台体） | 窗的下沿 + 盖住底部的水 | 54px 三档 |
| 山脊受光边 | 天光勾出山形（没有它山体是一块死色） | 1px，山体色向天空底带混 34% |
| 水岸线 | 山脚与湖面的分界 | 2px，近山色压暗 35% |
| 湖面反光条纹 | 水面质感（像素水面的标志） | 1–2px，行距 7px，透明度 0.16 |
| 涟漪 | 雨落湖面 | 1px 横线，宽度随寿命 4→20px 扩散 |
| 芦苇杆 | 前景剪影，随风轻摆 | 1–2px，穗 4×5px |
| 积雪边 | 雪天最强视觉信号 | 正弦厚度 0–11px，远山 35% / 近山 100% |

全部为**底纹档**（不承载分隔/引导/位置/状态语义），不进结构线白名单。

## 走过的假绿坑（写进 ADR，防再犯）

`world.spec.ts` 的「山脊轮廓」断言迭代了 **4 版**才真正有效，每一版都是绿的但都是假的：

| 版本 | 判据 | 为什么假绿 |
|---|---|---|
| ① | 逐列找「比天空暗」的第一处 | 天空本身是 6 条**水平**色带，抓到的是色带边界（每列同高 → 起伏 0） |
| ② | 逐列找「蓝度 B−G 骤降」 | ①天空底带偏白、夜里近山与天空都是深蓝，颜色分不开；②扫描窗放到地平线以下会命中**山影倒影**（镜像的山形同样有起伏） |
| ③ | 只测「有相邻行亮度骤降」 | 近山脊线的**受光边**（亮线）到山体本身就是一次骤降——把近山画成天空色时它照样存在 |
| ④ | 只测「比上方天空暗」 | 天空纵向本就渐亮，`bands[2]` 比 `bands[4]` 暗 → 假绿 |

**最终有效判据**：把**山色本身**拿到画布上数像素（色值取自源码 `sampleSky(alt)` 这一唯一事实源），
且只扫 `y < horizonY - 4`（排除水面倒影与 2px 水岸线）。
四个反例全部验证过必红：近山→`bands[2]`、近山→`bands[3]`、近山→`ridgeFar`、山脊振幅→0。

另一条经验：**深夜的天空顶部色（`#05081a`）与近山色（`#070b1e`）只差 2–4/通道**，
会撞进色值匹配的容差里 → 该用例固定到正午（`addInitScript` 覆写 `Date`）。

### 同一类坑的第二次：「水面比天顶暗」

守水面的第一条判据是「底部（0.92h）比顶部（0.12h）暗」——**它随钟点翻脸**：
真实夜空本就**近地平线最亮**（湖面镜像是地平线色带），深夜的水面确实亮过天顶。
改成**与山脊相对取样**（找「两条脊线都最低」的那一列，取它上方 4px 作天空基准、
地平线下方 20px 作水面），判据就与钟点无关。反例（水面 = 天空原色、无暗化）已验证必红。

> 取样用 `min(farRidge, nearRidge)` 而不是 `max`：山体是「脊线 → 地平线」**填充**，
> 取 `max` 会把取样点落进远山体内部，量到的是山不是天空。

### 第三次：几何改动之后，测试里的硬编码窗口全成了假的

把地平线从 0.68h 压到 0.80h 之后，三条 e2e 立刻红——**不是代码坏了，是测试在量别的东西**：

| 写死的量 | 失效方式 |
|---|---|
| 山脊扫描窗 `0.5h..0.66h` | 山体整体下移 → 窗口落空 |
| 水面条纹窗 `0.75h..0.95h` | 0.75h 已经在地平线**以上**（是山），而且窗台那几行不是水 |
| `genScenery(1440, 900)` | 画布宽是 **1424**（竖滚动条吃掉 clientWidth）→ 取样列落到另一座山脊上 |
| `sc.farRidge[x][1]` | `ridgeLine` 按 `step = round(w/220) ≈ 6` 抽点，**数组下标不是 x 坐标** → 必须用 `ridgeAt(pts, x)` |
| 取样列 `x = 10` | 落在**窗框**里（框宽 18px）→ 三个取样点全是框体色，判据变成「框 == 框」 |

**规矩：测试里凡是与场景几何有关的量，一律从 `genScenery(画布真实尺寸)` 派生，
不许写比例常数；数组一律用 `ridgeAt()` 取，不许下标索引。**

### 云的三条反馈（2026-09-21）

> 「云运动的太突兀了，不够自然」「太快了，像是匀速行驶」「每朵云的形状像是固定的」

三条全部成立，且各有明确根因：

| 症状 | 根因 | 修法 |
|---|---|---|
| 太快 | 近层 `vx = 0.34 px/帧` = 26 px/s，读作贴纸在滑 | `CLOUD.SPEED_*` 降到 0.17 / 0.075 |
| 匀速 | `c.x += c.vx`，`vx` 恒定；滚动视差还是另一个匀速叠加 | `cloudGust(t, ph)`：**两个不同频率的正弦相乘**（单频正弦的加减速可预测，看一会儿就知道节奏），输出 0.30–1.20，每朵云相位不同 → 云与云之间也不同步 |
| 形状固定 | `blocks` 是 **4 块写死的比例模板**，所有云只是缩放不同 | ①生成期：凸起 2–4 个、位置大小全随机、侧翼随机存在；②运行期：`morphCloud()` 每块各自的低频**整数**伸缩（平滑缩放会产生抗锯齿灰边、破像素语言）+ `cloudBob()` 垂直起伏 |

**像素云的形状变化必须是整数伸缩**：这是像素语言与「缩放」的分界——整数伸缩天然是
「这块像素多了一行」，非整数缩放则产生抗锯齿灰边。

## 代价与未结

- 每帧多两次 offscreen 重绘（天空半分辨率 + 山湖全分辨率），只在 `dim`/`resize`/帧切换时重算；
- 雨雪粒子全站飘，`rainDropCount` 钳在 320、`snowFlakeCount` 钳在 190；
- reduced-motion：降频不冻结；点亮仪式跳过；**雷闪禁用**（WCAG 2.3.1）。
- 未结：白天太阳光晕在浅色主题下是否够亮、雨天云层与 CRT 扫描线叠加是否有摩尔纹，
  留给作者观感验收。

## 附录（2026-09-25）：`core` 档退役，背景收敛为 world / off

作者裁决：「core 退役换成 world 背景」（起因：线上看到「背景弄没了」——浏览器里存着旧
`8bitme:bgfx=core`，而 core 只画暗底走线，看起来就像没有背景）。

- **模式表收敛**：`MODES = ['off', 'world']`，`DEFAULT_MODE = 'world'`；`normalize()` 把
  旧存值 `core`（以及 v4 五滤镜脏值）一律归一到 `world`——老访客不会停在老模式上。
- **实现整块删除**（不留死代码）：BgFx 的 `stepCore` / `drawCore` / 相机 / section 重组 /
  signal packet / 尘埃 / 待机灯，`bgfx-motion.ts` 的机器叙事族（`genMachineLayout` /
  `genManhattanTrace` / `cameraFor` / `contentBox` / `genSectionTargets` / `packetPos` /
  `ledPhase` / `dustSpawn` / `snap8` / `segHitsRect` / `chipPins` / `genRoute` /
  `genTracesFor`）连同 `coreGlow`/`GLOW` 与它们的两个单测文件一并退役。
- **保留**：`easeSilk` / `mix`（world 点亮仪式仍在用）、`lightThemeLineFactor`、
  `scrimCoverage`；双芯辉光**语言**仍由 PageTrans 的 CRT 光束独占（那是跨页签名）。
- **守卫**：`tests/unit/prefs.spec.ts` 的「bgfx 退役契约」锁模式表与删除面；
  `tests/e2e/toggles.spec.ts` 锁「core 存档 → WORLD + 画布真的在画世界」。
