# 像素字体下博客写作与排版的可读性约束报告

> 交付物：为 8bit-me「博客写作技能」（`.pi/skills/blog-writing/`）提供素材的离线调研报告。
> 日期：2026-09（与作者 09 盘问定案同轮）· 类型：研究方法论文档 · 不进技能本体，只作数据源
> 覆盖范围：8 篇存量文章（全量快扫 + 2 篇精读）× 排版层全部参数 × 写作层通用约束
> 推断来源标注约定：**【Zpix 设计格】**＝基于 Zpix 12px 像素网格的推理；**【通用 CJK 排版经验】**＝中文排印/阅读心理的通用经验值；**【像素阶梯对齐推理】**＝由"像素字 + 非整数度量 → 半像素错位"这一机制推出的结论；**【需作者人眼验证】**＝机制上成立但观感因人而异、必须用真实渲染裁决的点。

## 摘要（TL;DR）

**写作层定下限、排版层定上限，两层都有明确可执行的缺口。**

- **写作层现状（已定案的病根）**：8 篇平均句长 86~87 字（建议 ≤55）、加粗密度最高 16 处/千字（建议 ≤12）、括号递归与顿号链条把「一句一意」破坏成「一句多意」、长文条目化导致叙述断流、全文 0 站内互链。字多不是问题，**结构密度才是**。
- **排版层现状（本次量化发现）**：最致命的是 **prose 正文行高 `1.7` 在 14~16px 字号下算出 23.8~27.2px 的非整数行距**——像素字每行基线都落在半像素上，这是「阶梯不对格」的总根源；其次是 **prose 内部 h2=15.2px 小于正文 16px（层级倒挂）、h3=12.8px 低于自家"<14px 笔画并死"注释（下限被自己违反）**，以及全站只有 400 字重、`<strong>` 全靠浏览器 faux bold 合成（与写作层加粗密度叠加成双重损伤）。
- **一句话策略**：写作层把「每段一意、每句 ≤55 字、加粗只给术语首现」立成硬规范；排版层把「行距取整数像素、prose 型阶回到 8/12 倍数阶梯、小字档位回到 Zpix 原生 12px 格」落地——这两组动作不冲突、可并行，且都在作者本地预览可控范围内。

## 第一部分（A）· 像素字体可读性约束清单

> 本部分为"模型内建排版/阅读知识"的整理：先给写作层硬规范（内容怎么写），再给排版层参数建议（渲染如何配）。每条给「可执行数值 + 为什么」。

### A1 写作层规范（内容写法）

#### A1.1 段落长度上限

| 指标 | 建议值 | 为什么 |
|---|---|---|
| 单段字数 | **≤ 180~200 字**（@16px、36 字/行 ≈ 5~6 行） | 中文屏读的段落舒适区是 2~4 句、3~5 行；超过 6 行读者开始丢段落边界。【通用 CJK 排版经验】 |
| 单段句数 | 2~4 句 | 段 = 一个主张 + 至多两点支撑；句数超过 4，段落重心漂移。【通用 CJK 排版经验】 |
| 段首信息 | 首句即主张（结论句置顶） | 扫读路径是"段落首句 → 加粗 → 列表"；首句不表态的段落是扫读黑洞。 |

#### A1.2 句子节奏（本次差距最大的一项）

| 指标 | 建议值 | 为什么 |
|---|---|---|
| 单句字数（以句号/问号计） | **≤ 50~55 字**，超 60 必修 | 中文工作记忆约 4±2 块；主句每多一个逗号节/分号节，读者要额外持有一个待解引用。【通用 CJK 排版经验】 |
| 逗号节 | 一句 ≤ 2~3 个 | 超过 3 个逗号的句子，在加粗/行内代码并存时阅读成本指数上升。 |
| 分号 / 破折号 | 各 ≤ 1 处/句 | 「；」在中文里是"两个句子硬并进一句"，破折号是"句内再开注释线"——两者都打断主句推进。 |
| 括号 | **句内 ≤ 1 组**；括号内不再套括号 | 括号 = 阅读时的"岔路"；嵌套括号（`条目（工具名/认证/路径/模块/类名）`）让读者同时维护两层上下文。【通用 CJK 排版经验】 |

句子拆分的判据：把句子读出来，如果中途需要"回看主语"才能接上后半句，就拆。

#### A1.3 标题结构与层级密度

| 指标 | 建议值 | 为什么 |
|---|---|---|
| 层级数 | ≤ 3 级（h1→h2→h3） | 本站文章形态（方法论文/项目解说）3 级封顶；出现 h4 意味着章节需要重组。 |
| h2 章节标题 | ≤ 14~16 字，**编号+冒号+动宾/问题式**（如「一、注册表：把"加工具"变成"加配置"」） | 扫描者 2 秒内要从标题拿到"这节干什么"；纯名词标题（「注册表」）要给"要达成什么"。【通用 CJK 排版经验】 |
| h3 小节标题 | ≤ 12 字 | 比 h2 低一级即可，别做 h2 的复读。 |
| 编号体系 | 全站统一（推荐「一、二、三」或纯章节名，二选一） | 现状 8 篇里「一、」「第一章」「无编号」三种并存，跨篇阅读时层级预期不一致。 |
| 字数上限（h1） | ≤ 20 字 | 站内 h1 在单篇页是 18.4px 档，超长标题会直接折成两行，吃掉首屏。 |

#### A1.4 列表 / 加粗 / 行内代码的使用纪律

| 对象 | 建议值 | 为什么 |
|---|---|---|
| 列表项长度 | 每项 ≤ 2 行（≈70~80 字）；超 3 行 → 改"结论句 + 小段" | 列表的契约是"快速扫读每一项的开头";3 行以上的项 = 假列表，读者被迫整段细读，扫读失败。【通用 CJK 排版经验】 |
| 单个列表项数 | ≤ 7 项（7±2 工作记忆上限） | 超过 7 项加粗 lead 的列表，读者记不住前面项，只能反复回滚。【通用 CJK 排版经验·Miller】 |
| 加粗用途 | **二选一**：要么只加粗列表 lead（≤8 字术语），要么只加粗句中结论短句（≤8 字）——不要两种混用 | 混用时读者无法区分"这是术语"还是"这是重点"，加粗的可扫性归零。 |
| 加粗密度 | **每千字 ≤ 8~12 处**（现状最高 16） | 加粗是排版层稀缺资源（像素字无真粗体，见 A2.7），密度超标的收益是递减的：全粗 = 全不粗。 |
| 行内代码 | 句内 ≤ 2~3 个；**>12 字符的标识符/路径/正则一律移代码块** | 行内代码在正文行内形成"砖块"（背景色块），多了就把句子切成碎片。 |
| 顿号链 | 顿号并列 ≤ 3 项；4 项以上改列表 | 「A、B、C、D、E 均满足…」读到最后才知用途；列表让每项独立成行，扫读成本恒定为"扫一遍 lead"。 |

#### A1.5 扫读结构（每节讲一件事的推进方式）

- **段落推进**：结论句置顶 → 一个证据/经过 → 一句话收束。三步以内讲完一节，不展开第二主张。
- **节与节之间的桥**：长文（≥100 行）每 2~3 个 h2 后需要一个"叙述性过渡段"（1~2 句：上一节结论与下一节的关系）。现状文章章节间全是硬切，读感像跳帧。
- **开头钩 + 路线图**：首段 ≤ 50~80 字给钩（现状 OK）；**≥100 行长文应在开头 3 段内给一句"这篇分 N 部分：A / B / C"**（现状 8 篇全部缺失）。
- **结尾回扣**：末段回到开头主张（现状多篇已做到，是好模式，保留即可）。
- **每节一个"为什么"**：技术长文的最高扫读单元是"结论句+为什么"；每节能提炼出一句"为什么这么做"，该节就合格。

#### A1.6 中英混排与标点处理

| 规则 | 建议值 | 为什么 |
|---|---|---|
| 中英间距 | 中文与英文/数字之间空 1 格（`CDP 连接真实 Chrome`） | 像素字无光学间距补偿，中英贴在一起比矢量字体更糊。【通用 CJK 排版经验】 |
| 标点 | 全为中文字符标点（，。：；、——「」）；英文句内用半角 | 与站内语言约定（中文为主、术语留英文）配套。 |
| 引号 | 全站统一「」；嵌套用『』；代码/字段名用反引号或直引号 | 现状在一篇文章内出现 ASCII `"` 与「」混用（见 B2.1-8）。 |
| 中文里引用代码 | 反引号包裹，不裸写（写 `main.py` 而非 main.py） | 反引号 = 像素字体下明确的"代码块"语义标记，行内背景色由此而来。 |
| 术语 | 首现给一次中文注释，其后全用英文；不中英重复 | 「风控（risk control）」即可，不要每次「风控/risk control」都写双份——双份 = 每行多 30% 字符密度。 |

#### A1.7 技术长文的「密度-留白」配比

| 指标 | 建议值 | 为什么 |
|---|---|---|
| 结构停顿频率 | 每 300~400 字出现一个结构性停顿（标题/列表/代码块/空过渡段） | 连续 400 字纯叙述 = 一屏半无停顿，读者丢锚点。【通用 CJK 排版经验】 |
| 叙述文字 vs 列表体积 | 段落体积 ≥ 60%，列表/代码 ≤ 40% | 现状最严重的 data-pipeline 正文段落仅 12 个、其余全是列表——文章变成"清单"，没有阅读节奏。 |
| 连续列表 | 两个列表之间至少 1 句过渡 | 列表接列表 = 把判断责任全部丢给读者。 |
| 术语密度 | 每句 ≤ 2 个未解释术语 | 超过 2 个专业术语一句，等价于在外文里读注脚。 |

### A2 排版层参数建议（针对 Zpix 的具体数值）

> 前置物理事实：Zpix 是 12px 像素网格字体（SolidZORO，单一 400 字重）。**12px 整数倍（12/24/36/48…）渲染时像素阶梯完全对格；非 12 倍数（14/15/16px 等）时笔画宽度在相邻像素间跳变**，程度随缩放分母不同而不同。【Zpix 设计格】

#### A2.1 正文字号阶梯

| 字号档 | 建议 | 为什么 |
|---|---|---|
| 正文主档（桌面） | **16px**（12×4/3，非整数倍档） | 作者已锁 14px 下限（<14px 笔画并死）；16px 是全站阅读主档。【Zpix 设计格】 |
| 正文下限（移动） | 14px 地板，**不得再降** | 与现有 clamp 注释一致；14px 是 Zpix 可接受的缩放下限。 |
| 候选优档（可选实验） | 18px（=12×1.5，半整数倍）、24px（=12×2，整数倍） | 若作者人眼判定 16px 有笔画不均，18px 是比 16px 更"干净"的档位；24px 只适合展示型引言。**需作者人眼验证** |
| 禁用档 | 15.2 / 12.8 / 14.4 / 18.4 / 8.8px 等碎片档 | 全部不是 12 格也不是 8 格（8px 阶梯）的整数倍，像素对格无从谈起。【像素阶梯对齐推理】 |

#### A2.2 行宽上限（CJK 每行字数）

- **经验区间：30~40 字/行**；CJK 屏读 40 字为普遍上限，45 字以上久读疲劳陡增。【通用 CJK 排版经验】
- 现状实测：`.prose` 内容宽 = `42rem`(672px) − container padding 24px − pixel-panel padding 56px − 4px 边框 ×2 = **584px**，16px 字下 ≈ **36.5 字/行** —— 落在区间内，**达标**。
- 建议：**维持 36~37 字，守住 ≤40**。若未来加宽容器，`--content-max` 上限 45rem（约 40 字），不推荐超过。

#### A2.3 行距（像素对格 / 阶梯对齐）——本次最高优先级的参数缺口

- **机制**：像素字以整数网格为设计基准。行高若为分数（如 16px×1.7=27.2px），则**从第二行起每行基线都落在 0.2px 的亚像素偏移上**；关闭抗锯齿（本站 `-webkit-font-smoothing: none`）时，同一字形在不同行宽窄跳变，正文出现"行间笔画不均"的噪感。【像素阶梯对齐推理】
- **建议值**（按 4px 阶梯取整，`--step:4px` 与全站设计 tokens 同构）：

| 对象 | 现状 | 建议 | 为什么 |
|---|---|---|---|
| 正文 line-height | `1.7` → 14px 档 23.8px / 16px 档 27.2px（均非整数） | **28px 固定**（写作 `1.75rem` 或显式 px，不用单位倍数） | 28 = 4px 阶梯整数倍；对应 14px 字 ≈ 2.0 倍、16px 字 ≈ 1.75 倍，都在 CJK 舒适区（1.6~2.0），且移动端（14px）天然更疏朗。【像素阶梯对齐推理】 |
| 标题 line-height | 全局 `1.1` → 48px 档 52.8 / 32px 档 35.2 / 24px 档 26.4px | **取整到 4px 阶**：h1 56px、h2 36px、h3 28px、h4 20px | 标题多为单行，行距取整主要防多行标题两行几乎贴死；CJK 多行标题 1.1 会黏连，≥1.2 更稳。【像素阶梯对齐推理】 |
| pre 代码行距 | 继承 body | **20px**（14px 代码 ×1.43，4px 阶） | 代码块抗锯齿是矢量字体（Consolas），但整块行距不起伏更规整。 |

- **若 28px 观感偏松**：次选 24px（16px 字 1.5 倍，紧但可用）；**26/27px 一律不用**（非 4px 阶）。**需作者人眼验证**。

#### A2.4 列表与代码块的密度处理

| 对象 | 建议 | 为什么 |
|---|---|---|
| 列表项间距 | `li + li { margin-top: 0.5em }`（16px 字 → 8px，4px 阶） | 现状 li 无间距，2~3 行项首尾相接成"块"；8px 分隔恢复"每项一眼"的扫读契约。 |
| ul/ol 缩进 | 保持 1.5rem（24px） | 4px 阶，达标；不要再加缩进（行宽有限）。 |
| 行内代码 | `font-size ≥ 0.9em`、行高继承 | 现状 0.85em（14~16px 字下 11.9~13.6px）在像素行内显小、且非像素阶；0.9em 下 16px 字 = 14.4px 仍是碎片档，故**建议 0.875em→14px 或直接 0.9em 配合 A2.1 的字号归整**。 |
| pre 内代码 | `0.875rem`（14px 整数档）、内边距取 4px 阶 | 代码块是"阅读单元"，14px 是矢量 mono 的舒适下限；1rem=16px 内边距达标。 |
| pre 边框 | `3px → 4px` | 全站像素语言都是 4px 边框（pixel-panel/border-top 4px），pre 的 3px 是孤例，破坏对格。【像素阶梯对齐推理】 |

#### A2.5 加粗在像素字体下的呈现风险（写作层 × 排版层的交汇点）

- **风险机制**：站内 @font-face 只声明了 `font-weight: 400`——**不存在真粗体**。`<strong>` 触发浏览器 faux bold（对字形做像素位移/二次描边合成）。关闭抗锯齿的像素字在 faux bold 下会出现**笔画错位、重影、字形变糊**，14~16px 档位尤其明显。【像素阶梯对齐推理】
- **三条出路（三选一，需作者人眼验证后定案）**：
  1. **接受 faux bold**：保留写作层现有加粗习惯，CSS 显式 `strong { font-weight: 700 }`，作者在 16px 档截图验收一次，作为全站基线；
  2. **稀释加粗**：按 A1.4 把密度压到 ≤10 处/千字 + 只加粗短术语（≤8 字），让 faux bold 的总量降到可接受；
  3. **像素高亮替代**：把"强调"改由 `.hl` 类（背景色块/下边框，如 tag 的 2px 边框语法）表达，正文只留术语性加粗。
- **结论**：无论选哪条，**写作层必须先降密度**——否则排版层无论怎么调，faux bold 总量在那里。

#### A2.6 其它参数微调

| 对象 | 现状 | 建议 | 为什么 |
|---|---|---|---|
| body letter-spacing | `0.5px` | **0**（CJK 零字距天然等距） | 像素字下 +0.5px 会给每个汉字加非像素阶间距，破坏字与字之间的格点；拉丁字母需要可单独在标题用。【像素阶梯对齐推理】 |
| 标题 letter-spacing | `-0.02em` | 0 或保留但验证不粘连 | 负字距在像素字体里可能让相邻字形笔画重叠 1px；32px 档 -0.64px 有粘连风险。【需作者人眼验证】 |
| 语义小字号（tag/meta） | 0.55rem(8.8px) / 0.8rem(12.8px) 等 | **收回到 Zpix 原生 12px 格（0.75rem）或 14px 地板** | 8.8px 在 Zpix 下是非整数缩放、笔画并死的重灾区——它自己违反了 global.css「<14px 笔画并死」注释。若为"丝印装饰感"有意为之，须在 CSS 注释显式声明豁免并接受此档不承载阅读功能。【Zpix 设计格】 |
| prose h2/h3 | 0.95rem(15.2px) / 0.8rem(12.8px) | **h2 ≥ 1.25rem(20px) 或 1.5rem(24px)；h3 = 1.125rem(18px)** | 见 B3 逐条对照：15.2px 与正文 16px 倒挂、12.8px 低于像素下限，是与全局 8 倍型阶脱节的两处最大失误。 |
| 单篇 h1 | 1.15rem(18.4px) | 1.125rem(18px) 或 1.25rem(20px) | 18.4px 非 8/12 格；18px 是 12×1.5 半整数倍，20px 是 12×5/3 又非……**以 18px 为推荐**，观感接近且对格更稳。【Zpix 设计格】 |

#### 写作层共性问题（W1~W10，按影响排序）

- **W1 平均句长显著超标：约 86~87 字/句**（精读两篇）。建议 ≤55。这是所有问题里对"读"伤害最大的一项——句子越长，行内加粗、行内代码、括号的作用越互相干扰。
- **W2 加粗密度超标且双重用法混用**：data-pipeline 35 处/2127 字（≈16 处/千字）；且"术语 lead 加粗（`**唯一入口**：`）"与"句中强调加粗（`——**立即中断、不重试**——`）"并存，读者无法用加粗做扫读索引。全站最粗的 5 篇全是方法论长文，加粗既是优点（可扫）也是缺陷（全粗=全不粗）。
- **W3 括号递归与括号内枚举**：v2 重构 55 个括号/3123 字（≈1.76%/字）；data-pipeline 出现 `（工具名 / 认证方式 / 数据库路径 / 入口模块 / GUI 类名）` 这种括号内 5 项枚举。括号 = 阅读岔路，堆叠 = 读者同时走多条岔路。
- **W4 长文条目化、叙述断流**：data-pipeline 全文正文段落仅 12 个，文章 80% 体积是列表与短 bullet；v2 重构、RPA 迁移、黑盒逆向同病（叙述段落 11~25 个）。列表堆叠让"为什么"链断裂——读者拿到的是清单而非论证。
- **W5 顿号链条滥用**：4 篇方法论文章顿号 16~34 个/篇（约每 60~130 字一个），4 项以上并列仍用顿号而非列表（如`cookie 关键字段 + CSRF 令牌三重校验`这类混合符位列）。
- **W6 引号体系不统一**：8 篇内 7 篇用「」（与站内语言约定一致），但 data-pipeline 一篇内既有「」又有 ASCII `"`（`把"加工具"变成"加配置"`、`把"像人"工程化`）。
- **W7 站内互链为零**：8 篇 **0 个 markdown 链接**，而 data-pipeline 结尾明写「和这个站其它几篇的结论一致」、plasma 写「和 RPA 迁移里…同款」，都是现成的互链挂点——双轨内容库里 5 篇方法论同源同风格，互链是零成本的结构资产。
- **W8 章节编号体系三套并存**：「一、二、三」（data-pipeline）、「第一章/第二章/第三章」（v2 重构）、无编号（v1 walkthrough、astro notes）。跨篇阅读时的层级预期不一致。
- **W9 长文缺路线图**：4 篇 ≥90 行的文章开头均无「本篇分 N 部分」预告；好在首段钩子普遍合格（v1 walkthrough 直接点题、data-pipeline 用"深渊"钩子），保留此模式即可。
- **W10 层级扁平**：h3 在多数文章里近乎缺席（data-pipeline 全文仅 1 个 h3「节奏控制」），把"章节内再分组"的职责压给了超长 bullet。

#### 排版层共性问题（P1~P10）

- **P1 行高非整数**：`line-height: 1.7` × 14~16px 字号 = 23.8~27.2px，全站正文基线不对 4px 格（剖面最深的问题）。【像素阶梯对齐推理】

- **P4 小字突破自家像素下限**：global.css 明写「像素字 <14px 笔画并死」，但 `.tag` 8.8px、`.meta` 12.8px、`.cover-tag` 7.2px、`.back` 9.6px、`.fx-toggle` 8.8px 全线低于 14px。

## 附录：作者人眼验收矩阵（建议的验证步骤）

> 以下验证均为"本地 `npm run dev` + 浏览器截图对比"，无需部署，符合 开发流程文档 验收纪律。

1. **行距档位 A/B**：把 body line-height 临时改为 24/26/28/30px 四档，各截一段含加粗+行内代码+列表的正文（建议用 data-pipeline「共享层归一」段），对比像素阶梯是否均匀、行间是否黏连。

## 来源与标注汇总

- 【Zpix 设计格】：Zpix 为 SolidZORO 制作的 12px 像素网格字体，全站仅 400 字重（@font-face 仅声明 font-weight 400），设计格 12px 为站内已知事实（global.css 注释"像素字 <14px 笔画并死"即由此来）。
- 【通用 CJK 排版经验】：句子工作记忆 4±2（Miller）、CJK 屏读行宽 30~40 字、段落 3~5 行、中文一句 ≤2~3 逗号节等，均为中文排印与阅读心理学的通用经验区间，非本站特有。
- 【像素阶梯对齐推理】：像素字以整数网格设计 → 任何非整数度量（行高、字距、字号缩放）都会让字形落在亚像素位 → 关闭抗锯齿（本站已做）时表现为笔画宽窄跳变/基线不对格。此机制适用于任何像素字体，不依赖 Zpix 特殊性。
- 【需作者人眼验证】：14/15/16/18/24px 的字号观感、faux bold 是否可接受、286 档行距观感、小字豁免与否——这些是"机制成立但观感因人而异"的项，只能以真实渲染裁决，不得仅凭推理定稿。
