# 把「无序迁移」做成体系

接到一份「迁移活」时，最常见的心态是：把交付物搬过去、录上、能跑就行。
这篇把一次**跨多个业务实例的存量流程迁移**讲成一套体系——不是为了展示
某个技术栈，而是因为这套纪律独立于技术栈，任何「接手乱摊子」的工程都用得上。

## 背景：迁移从来不是「搬文件」

存量流程散落在影刀 xbot（无代码自动化平台，界面编排 + 少量脚本）上，要整体迁到
自研的 Python 体系里。真实约束：

- **1:1 迁移，不重构**。原版有什么，迁移后就得有什么——包括看起来多余的
  未注册类、废弃方法、注释掉的代码。原则是「宁可多不可少」。
- **编码映射逐字保留**。业务字段的字典编码（省市区、诊断项、状态枚举）是
  多年沉淀的资产，迁移中丢掉任何一个映射都是事故。
- 覆盖**多个业务实例**，每个实例的默认配置、编码字典、甚至厂商后端都不同。

规模一大，「搬文件」就变成了「搬不确定性」。方法论的每一层都是在对不确定性
做显式化。

## 第一性原理：协议是唯一事实源

迁移中最大的坑是**猜**。接口的请求参数、响应结构、编码映射到底长什么样——
平台界面不会告诉你，文档不会告诉你，只有抓到的真实流量会。

铁律两条：

1. **参数与响应格式以 HAR（真实流量记录）为准，禁止猜测**。编码映射必须从
   接口的字段字典里提取，禁止凭经验手写。副作用类接口（只写不读、没返回值）
   也必须在分析清单里，漏掉一个就漏一段业务。
2. **编码映射的动态化**：硬编码的映射表要换成「规则表不写死在代码里，从
   配置文件动态提取 + 快照 + diff」的机制。规则改了，快照能告诉你改了什么。

这条纪律的副产品是一个完整的**接口事实清单**，它同时是迁移的验收底座。

## 防御式工程纪律：失败要响、成功要验

迁移里「看起来成功」比「看起来失败」更危险。三件事锁死：

- **Fast Failed**：输入校验前置、尽早返回、显式错误码不吞异常；启动即检查
  依赖/配置/连接，失败即停。跑了半小时才发现配置错了，是最贵的失败。
- **保存后反查（save-then-verify）**：高危写操作走多阶段——
  重复检查 → 前置校验 → 必填校验 → 保存 → 反查。反查不是再调一次查询接口就
  完了：要复用现成查询方法做「中文对中文」的直比；编码字段跨接口不稳定时按
  key 比；接口不返回的字段「有值才比、无值跳过」，别拿缺字段当不一致。
- **映射失败必须抛错**：禁止 warning 跳过、静默吞差异。一次「先记下来以后看」
  的差异，就是日后线上事故的种子。这条原则是用真实教训换来的——某个实例的
  更新接口曾因吞掉映射差异而带错数据，此后全组立规：要么对，要么报错。

## 迁移的机械力：把 9 个坑变成检查清单

真实迁移路上踩过的坑，几乎全是「机械操作」层面的，值得原样记住：

- **模块导入 vs 属性导入混淆**：`from . import X` 被误转成 `from .X import X`，
  一次造成 20+ 处循环导入——对照源文件逐处区分同名导入。
- **变量名被当成子模块路径解析**、**正则漏跨行**：脚本层面的批量替换必须
  双人对照检查。
- **脚本漏替换源目录**：某区实例误迁进了另一区的文件——修脚本重跑 + 手工兜底。
- **注释残留前缀**（`@Desc` 等）导致对照脚本定位失败：手工修。
- **子模块路径连字符 vs 下划线**、`.git/modules` 需重建：版本体系依赖的坑。
- **注册表缺括号**：平台注册项的机械错误，靠清单核对兜住。
- **create 与 edit 的 payload 模板不可互套**：`pageType`、`queryString`、
  `batchid` 等系统字段在两种操作间有差异，批量替换拿错模板必错——
  逐字段对照 HAR。

这些坑单个看都很蠢，但它们的共同点是：**批量替换是盲目的，只有逐字段对比
校验是有视力的**。所以流程里补上「完成后逐字段对比」这最后一步，才敢说迁完。

## 公共层：消灭重复，才叫体系

迁移以「拷贝」开局是必然的（快速对齐现有实例），但拷贝必须收敛。三层收敛：

1. **公共基础包**：数据访问、协议封装、工具、日志、消息推送收敛成一个只读
   引用源，多个实例统一引用，消灭拷贝。
2. **清洗逻辑公共库**：各实例同源但微异的清洗逻辑（如诊断文本拆分、日期
   边界、身份证校验）收敛成公共模块，用**开关配置**而不是复制代码来区分
   实例差异——这就是「消除版本漂移」的正解。
3. **版本子模块 + 固定提交顺序**：公共包作为 git 子模块被多个项目引用，因此
   有了强制顺序——**先推子模块，再推父项目**，否则父项目指向不存在的 commit。

再往上一层，是面向「多个实例」的元工具：**统一构建 CLI**，一条命令遍历所有
实例做版本号管理（本地/远程对比、patch/minor/major）、构建前安全检查
（未提交文件、敏感文件保护拦截）、日志轮转。到这一步，「迁移」才算结束，
「运营一个体系」才开始。

## 迁移的 AI 属性：先立约束，再谈产能

前几章没有挑明的一个事实：这场迁移的**主力是 AI 编程工具，不是人手**。
1:1 等价迁移规范、编码映射逐字保留、踩坑清单——这些纪律如果只对着人讲，
就讲窄了；它们真正的对象是 AI。

- **多 Agent 并行调研与独立审查**：迁移路径由多个 Agent 并行起草，再由独立
  审查核对行为等价。审查是纪律的一部分，不是事后补救。
- **1:1 等价规范是给 AI 的行为约束**：禁止重构、编码映射逐字保留、宁多勿少；
  行为等价，才可自动验证。
- **踩坑清单就是给 AI 的提示词**：9 条坑全部是批量替换阶段的真实事故，
  固化成清单后成为验收的固定环节。
- **规模与版本**：Python 3.7 → 3.12 全面升级，覆盖存量全部业务线；
  行数与实例数一律隐去。

AI 在这里不是「写得更快的加速器」，而是**被纪律化之后的工程产能**。
AI 越强，约束越要先立——这正是工程化方法论者对 AI 的态度。

## 写在最后：迁移工程的本质

回头看，这套方法论没有一条是「RPA 专属」的，它们全部是**对不确定性的
显式化**：

- 事实源是什么 → 用 HAR/协议锁定，不猜；
- 结果对不对 → 保存后反查，用中文直比；
- 失败怎么处理 → 快失败、必报错，绝不静默；
- 谁改了公共的东西 → 子模块记录 + CLI 管版本 + 提交顺序立规矩；
- 教训怎么留 → 每一条内联进规范，并注明它来自哪个实例、哪个教训。

把「搬文件」变成「搬确定性」，迁移就不再是冒险，而是可验收、可追溯、
可复用的工程。这套打法，换任何一套技术栈都成立。
