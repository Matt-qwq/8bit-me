六个脚本的收敛：加平台从写脚本变成加配置

2026-08-29·Python配置驱动工具链方法论

一套多工具体系要加新成员，真正的成本往往不在代码，而在入口与约束。六个相互独立的脚本，就是这段历史的起点：每加一个平台，就得再添一个脚本，入口散，约束靠自觉。

后来体系收敛成一个入口、一张注册表（registry，声明工具的清单文件）。本文不评价它好不好用，只回答一个问题：它为什么长成现在这样，而不是别的样子。每个设计决定都对着一个痛点，先找痛点，再看答案。

本篇分 5 部分：先看散脚本的痛点，再依次讲入口收敛、约束收敛，接着讲两条写死的红线，最后划边界。文末还会交代：这套办法在什么条件下会失灵。

一、起点：散脚本为什么撑不住

散脚本的第一笔账，记在入口上。脚本跟着平台走，入口就跟着平台走；用的人得记清「哪个脚本管哪件事」，自动化要对每份脚本单独接线。

第二笔账，记在约束上。什么能做、什么不能做，全凭各脚本自行把握，体系里没有任何一层强制检查。只靠记得的约束，效力取决于人当时的注意力；换个接手的人，约束就可能悄悄断档。

两笔账指向同一个结论：散结构把体系的责任，压给了人的记忆与自律。要长期地跑，体系得把这两样从人脑挪进代码与配置。先动最好动的那样：入口。

二、第一次收敛：入口合一

第一次收敛，是让所有工具共用一个入口。改造后体系只剩一个 main.py，它同时是 GUI（图形界面）启动器与 CLI（命令行界面）。

双形态不是贪多，而是两种场景各取所需。GUI 留给盯着屏幕的人：挑工具、看状态；CLI 留给脚本与定时调度：无人值守时也能完成启停与导出。两条路背后是同一套实现，人用与机用不会各漂移一份。

CLI 的命令集固定如下：

list | status | start | stop | export | analyze    # 定时调度

命令收口后，人、脚本与调度器只认同一套动词。可入口统一只解决「从哪进」，约束仍是空白：每个工具靠什么管住自己，还是各凭自觉。入口合拢了，约束呢？

三、第二次收敛：约束进配置

第二次收敛，是让每个工具在注册表里各占一条。条目是声明式的：只描述事实，不描述过程。一条声明写清四件事：

  • 认证方式：它如何取得凭证。
  • 数据库路径：数据落在哪个本地文件。
  • 入口模块：真正干活的代码在哪个模块。
  • GUI 类名：图形面板由哪个类实例化。

声明把工具的相貌，从散落的代码里抽出来，收进一处。想弄清某个工具怎么认证、数据在哪，不必翻它的脚本，读配置即可。

声明之外，还有三个协议函数：declare、status、start。名字即职责：declare 登记，status 报状态，start 启动。注册表管「是什么」，协议管「怎么动」。

declare 的角色要单独分清：它不是运行动作，而是登记声明——让入口知道这个工具有什么、能做什么。运行职责归 status、start。

新增一个工具因此只剩两步：追加一条声明，实现三个函数。工具彼此不 import、不依赖，删掉一个不影响其余。体系的成长，被压进一条可复述的增量协议。

鸭子类型：只认形状

鸭子类型（duck typing）只认行为，不认类型。调用方只问对象会不会做某件事，不查它属于哪个类。main 按约定调用 status 与 start，从不检查工具是否继承了父类。

选鸭子类型而非继承树，是因为共享的形状太薄。六个工具真正共有的，只有「能被启动、能报状态」这一层。为这么薄的共性造继承树，等于把耦合写进类型血缘；日后想改一个工具，先得掂量会不会震到整棵树。鸭子类型把耦合收窄到调用约定，实现随各工具自由。

鸭子类型还有一层容易被忽略的保障：实现若缺了函数，调用那一刻就会报错，而不是悄悄跑偏。协议不设基类，等于把第一声失败交给运行时。

不设注册中心

同样被省掉的，还有注册中心（registry center，服务动态注册与发现的组件）。工具都从同一个 main.py 起来，进程内就能问清谁活着；再架一个中心，纯属给单机问题配分布式零件。静态配置表够用时，动态中心只是多余的移动部件。

注册中心解决的是另一类问题：工具散在多台机器、规模动态增减、需要运行时互相发现。这套体系的工具全在本地、全由一个入口拉起，没有那个前提。入口与约束都进了结构，剩下的运行时碰撞，就交给两道红线。

四、两条红线：单实例与零网络

注册表与协议管「工具是什么、怎么被调用」，还有两件事要管到禁止级。它们是绝对禁止并发与平台层零网络两条红线。下面拆开各自的动机。

单实例：双保险守卫

并发要禁，是因为工具都要读写自己的本地数据文件。同一份文件被两个进程同时打开，坏的不是数据就是状态，而双开没有任何收益。收益为零、风险实打实，就把它从纪律升格为结构。

守卫由两道保险组成，各防一类故障。落盘锁管正常竞争：后来的实例发现锁已存在，直接退出。进程存活探测管崩溃残留：持锁者已经死了，一道死锁不该堵死整个体系。两道缺一不可，只有锁会留下搬不走的死锁，只有探测则谁也拦不住同时起步的实例。

零网络：禁令即结构

零网络这条红线，划在平台层。状态查询只读本地 DuckDB（嵌入式分析数据库），根本不出本机。requests（HTTP 请求库）与 playwright（浏览器自动化库）在平台层禁止 import。

禁令的深意不在禁网本身，而在禁止的方式。import 是静态语句，可被脚本扫描，也可写进测试断言。「别联网」若只写进文档，检查它就靠人再读一遍文档。

两条红线的共同主题，是把关键约束写死在结构里。自觉可以被忘记，结构没有遗忘这回事。

五、边界：解决什么、不解决什么

这套设计解决三类问题：入口唯一、增量便宜、约束可验。加一个平台，降为加一条声明与三个函数。通用命令对每个工具一视同仁，因为每个工具都暴露同一组协议。红线长在结构里，违背即暴露，不必等人记得去查。

它不解决协议背后的任何事。注册表承诺的是形状，也就是 declare、status、start 三个函数在。形状之内的事情，比如取数质量、平台对抗、数据正确性，仍归各工具自己扛。声明管得了「工具长什么样」，管不了内容。

那么，这套办法什么时候失灵？

  • 成员之间没有共同的「可启动、可报状态」形状：注册表只是给简单工具套壳。
  • 工具数量小，且不再增长：静态配置未必比直白的代码更划算。
  • 协作跨机器、规模大到需要动态发现：该让位给注册中心。

判断标准一句话：有共享的形状，也有持续的增量，注册表就值；缺一样，它只是装饰。

回看开头：散脚本把入口与约束压在人的记忆里。收敛走完一遍，这两样责任从人脑搬进结构：加一个平台，从写一个新脚本，变成加一条声明与三个函数。而这条路的前提，是工具共享同一副形状、愿守同一套本地约束；形状一旦散去，注册表就只是好看的皮。
