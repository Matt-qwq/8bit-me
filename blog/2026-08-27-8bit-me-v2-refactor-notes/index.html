8bit-me v2 重构手记：可维护优先，决策留档

2026-08-27·8bit-meNetlifydesign tokenscanvasWeb Audio

2026-08 的 v2 重构一次动了三条线：架构与托管、主题系统与视觉引擎。表面是换托管、加主题和写动画，里面只有一个目的——让 AI 接手这个站时少踩坑。三条线看似独立，其实共享同一条底线：可维护性优先，决策全部留档。

本篇分 3 部分：架构与托管（ADR-0001）、主题单一数据源、零依赖 bg-fx 动画。每部分按「决策 → 落地 → 验证 → 坑 → 沉淀」推进，收尾统一回到那条底线。

一、架构：站点公开，源码私有

问题：仓库该不该公开

v2 的第一个架构决策，是把「站点公开」和「源码公开」拆成两件事。站点内容是作品集：要发简历、给 HR 看，注定公开。源码是另一回事——AI 维护的代码加完整方案，放进 public 仓库等于把内部设计全部摊开。

GitHub Pages 免费档强制仓库 public，「站点公开」和「源码公开」只能同进退。解法是拆开：仓库 private、站点 public——访问者只见渲染产物，源码只对站主可见。GitHub Pages 满足不了私有仓，托管只能另选。

托管实测与迁移

先看托管候选，标准只有一个：国内直连要通，自己的站得打得开。四个平台当时的实测结果：

  • github.io：国内可达
  • netlify.app：国内可达
  • *.workers.dev、*.pages.dev（Cloudflare）：被墙
  • *.vercel.app：被墙

初选落在 Cloudflare Pages：免费，又支持私有仓构建。上线后实测——Workers 部署与 pages.dev 域名国内直连不通，自己的站自己打不开。换成 Netlify 才落地：免费档、GitHub App 连私有仓，且 .netlify.app 国内可达。

Netlify 也埋着一个默认值坑。2026-07-28 后新建的团队，新项目默认 private（site protection）。于是新站一律弹 401 登录页——要手动把 Project visibility 改回 Public。

框架：维持 Astro 7

框架没换，维持 Astro 7。它是 registry 最新主版本，也是唯一同时满足五条约束的选项。「喜欢新技术」和「AI 维护成本低」在这里并不冲突，约束如下：

  • 静态站
  • markdown 内容管线
  • 零迁移成本
  • v2 canvas 扩展
  • 免费托管

部署契约

迁移真正的坑，集中在四个部署参数上。它们都曾是静默错误。默认 base 还停在 /8bit-me/——那是 GitHub Pages 子路径时代的遗留。四条如今写死成契约，逐条如下：

  1. 注入 ASTRO_BASE=/，产物不再落子路径，canonical 不再错位。
  2. 注入 ASTRO_SITE：它决定 canonical 与 og:url，漏了就静默指回旧域名。
  3. netlify.toml 的构建设置优先于 UI 配置（官方文档明示）。
  4. 每次 push main 触发生产构建——内容即代码，写 markdown 即上线。

typecheck 门禁因此写进构建命令，随这次 code review 一起恢复。命令本体只有一行：

command = "npm run typecheck && npm run build"

这套「决策文档化 + 评审」的流程，对 AI 维护的站尤其重要。任何 agent 读 CONTEXT.md 与 docs/adr/，就能还原每一条为什么。决策都留了档，可代码里还压着一笔「一份数据、两个源头」的债——主题系统首当其冲。

二、主题：收敛成单一数据源

v1 的双源长在主题系统里：同一份色值，同时写在两处。一处是 src/lib/themes.ts，面板与色板条都在读。另一处是 global.css 里手写的 13 套 [data-theme] 规则块。

给主题加一种配色，就要同步改两处——tsc 只保证 key 合法，保证不了颜色一致。重构目标压成一句：加主题只改一个文件。

生成色块，不手写

主题块改为构建期生成：BaseLayout.astro 遍历 THEMES，直出 CSS 进 head。核心是这一次 map：

const themeCss = THEMES.map(
  (t) =>
    `:root[data-theme="${t.key}"]{` +
    `--c-bg:${t.colors[0]};` +
    `--c-line:${t.colors[1]};` +
    `--c-accent:${t.colors[2]};` +
    `--c-text:${t.colors[3]};}`,
).join('\n');

global.css 只留 :root：默认色加语义别名（如 --color-text）。主题块只覆盖 --c-bg..3，别名在消费处由 var() 解析。深层嵌套组件因此零改动。

等价性验证

生成代替手写，等价性是前提；评审时专门核过整条 var() 链路。选择器 :root[data-theme] 的优先级是 (0,2,0)。它压过 :root 的 (0,1,0)，--gb-* 的覆盖成立。

custom property 在声明处代入、再随继承下传。13 套色值逐一与旧手写块比对，大小写无关、数值一致 √。

CRT 换主题色

主题化要覆盖到最上层的 CRT：扫描线原先是写死的绿。它硬编码 rgba(15,56,15,…)，任何主题下都是同一条绿线。现在改吃对比色槽 --c-text，不再吃背景槽 --c-bg。

为什么不吃背景槽？浅色主题下它约等于背景色，扫描线会直接隐形。这条回归是 code review 抓出来的。半透明交给 color-mix，由主题色现算：

:root {
  --crt-scan: color-mix(
    in srgb, var(--c-text) 35%, transparent
  );
  --crt-vignette: color-mix(
    in srgb, var(--c-text) 45%, transparent
  );
}

旧浏览器不认 color-mix，走 @supports 回退分支。回退值是固定近似色，观感差别可接受。

沉淀：消除第二个源

「以防万一」的同步注释，是双源里最贵的一句——同步注释是谎言。有同步约束，正确做法是消灭第二个源，不是靠注释提醒自己。加主题从「改两处、再祈祷」变成「数组加一项」——这正是 AI 维护想要的形态。

三、bg-fx：零依赖的辉光引擎

同一个成本账，在视觉层也算了一遍：背景动画要不要引入渲染库？hero 首屏的 bg-fx（背景特效引擎）是 v2 的主实验，答案是零依赖。

引擎同时服务六种观感：星尘 / 扫描 / 雨 / 波形 / 网格 / 关闭。全程零依赖，全站只有 astro 一个包。

质感从哪来

平涂小像素是「简陋感」的来源，电子感靠三件事撑起来。加法辉光管亮度，分层管纵深，脉冲管呼吸。

加法辉光负责亮：光晕层用 lighter 反复叠画，越叠越亮。深色主题才开加法，核心层走 source-over；浅色主题退回普通叠加防洗白。背景亮度只在主题切换时重算，不逐帧算。

glow.globalCompositeOperation = 'lighter'; // 光晕层
core.globalCompositeOperation = 'source-over';

分层负责纵深：星尘分前景和背景两层，前景走 accent、背景走 light。流星再拖一条渐隐尾迹。WAVE 模式叠三层：辉光→波形→镜像倒影。

脉冲负责呼吸：全局亮度按 0.75 + 0.25·sin(t) 轻轻起伏。公式不贵，效果是整片星尘都活了。

音画联动：事件解耦

点按反馈要音画同出，做法是先解耦：声音归音效模块，光效归 bg-fx，两边只认一个事件。音效模块在合成声音后统一派发，派发就一行：

// src/lib/sfx.ts：playClick / playHover / playNav 共用
window.dispatchEvent(new CustomEvent('8bit:fx'));

bg-fx 监听事件后各归各位：click 扩散波纹，nav 全屏扫光，hover 星火。两边只认事件名——声音与画面零耦合，加新音效、加新光效都不用动对方。

性能预算

静态站没有运行时中间层兜底，动画预算必须一开始就锁死。五条，条条是硬规则：

  • devicePixelRatio 封顶 1.5
  • 粒子数按 canvas 面积裁剪：clamp(area/9000, 70, 170)
  • hero 滚出视口（IntersectionObserver）、标签页隐藏即停帧
  • 样式串预生成，避免逐帧拼 rgba() 字符串
  • 坐标全部整数化（fillRect），天然防锯齿

坑一：启动门禁自锁

第一个坑是启动死锁，症状是画面完全静止。启动门 wantsRun() 里含 running 标志。而 running 只能由 sync() 开启——门禁等不到开闸的人，动画永远起不来。

修法：门禁只读外部条件——视口可见、页面可见，把自身状态请出判断。这条后来成了新启动条件都过的自查：门禁不读自身状态。

坑二：减动效别冻结

第二个坑来自一份好意：尊重系统减动效偏好（reduced-motion）。初版做成「渲染一帧静态画面」——对装饰性背景，这是过度执行。用户关动效要的是克制，不是死寂。

改法是把冻结换成半速：每两帧才推进一步。既守约定，又留活力——降频而不冻结。它后来长成全站减动效约定的默认项：装饰动画降频、不冻结。

收尾：切面独立，底线共享

三块切面，三个战场：托管在平台与配置间腾挪，主题在数据源里做减法，动画在依赖与预算上做克制。它们独立落地，却反复回答同一个问题——怎么让 AI 接手时少踩坑。答案各不同，底线只有一条。

零依赖不是抠门，它是让维护和预算同时变简单的架构选择。canvas 2D 出得了辉光质感，就永远不需要渲染库。

三块切面各有答案，可维护性优先的底线没变。改动有据可查，靠的是决策全部留档——站点因此改得动、查得到，AI 接手时自然少踩坑。
