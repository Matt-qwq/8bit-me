把「无序迁移」做成体系：一次跨实例 RPA 迁建的方法论

2026-08-29·RPA迁移工程方法论工程纪律

复盘整理：跨多实例 RPA 迁移工程（主体完成于 2026-08，留有少量遗留流程），本文整理于同月。

接到「迁移活」，最常见的心态是搬过去、能跑就行。这套思路摊到多个业务实例上，就变成了「搬不确定性」——接口参数、编码映射、公共逻辑全靠猜。迁移不是搬文件，是把不确定性显式化。

存量流程散落在影刀 xbot（无代码自动化平台）上，要整体迁到自研 Python 体系。约束三条，先说清。本篇分 5 部分：先讲事实源与防御纪律，再整理踩坑清单与公共层，最后谈 AI 属性。

  • 1:1 迁移，不重构。原版有什么，迁移后就得有什么，宁可多不可少。
  • 编码映射逐字保留。字典编码（省市区、诊断项、状态枚举）丢一个都是事故。
  • 覆盖多个业务实例。默认配置、编码字典、甚至厂商后端都不同。

这条流水线自下而上单向走，每一跳都得能交代来历：

四条纪律（固定提交顺序 / 快失败 / 要么对要么报错 / 映射失败必抛错）不属于 RPA 技术栈，换任何一套技术栈、接任何乱摊子都成立。

一、事实源：协议锁定，不猜

迁移中最大的坑是猜。接口的请求参数、响应结构、编码映射到底长什么样——平台界面不告诉你，文档不告诉你，只有抓到的真实流量会。

铁律第一条，参数与响应格式以 HAR（HTTP Archive，真实流量记录）为准，禁止猜测。编码映射必须从接口的字段字典里提取，禁止凭经验手写。副作用类接口（只写不读、没返回值）也要进分析清单，漏掉一个就漏一段业务。

铁律第二条，编码映射要动态化。硬编码映射表换成「规则表不写死在代码里，从配置文件动态提取，配快照与 diff」的机制。规则改了，快照能告诉你改了什么。

这条纪律的副产品，是一个完整的接口事实清单，它同时是迁移的验收底座。事实不留猜，变更必显形。

事实锁定了，怎么保证每一步都对？

二、防御纪律：失败要响，成功要验

迁移里「看起来成功」比「看起来失败」更危险。三件事锁死。

第一条，快失败（Fast Failed）。输入校验前置、尽早返回、显式错误码不吞异常；启动即检查依赖、配置、连接，失败即停。跑了半小时才发现配置错了，是最贵的失败。

第二条，保存后反查（save-then-verify）。高危写操作走多阶段：重复检查 → 前置校验 → 必填校验 → 保存 → 反查。反查不是再调一次查询接口就完事，三条细则：

  • 复用现成查询方法，做「中文对中文」直比。
  • 编码字段跨接口不稳定时，按 key 比。
  • 接口不返回的字段「有值才比、无值跳过」，别拿缺字段当不一致。

第三条，映射失败必须抛错。禁止 warning 跳过、静默吞差异。一次「先记下来以后看」的差异，就是日后线上事故的种子。

这条原则是用真实教训换来的。某个实例的更新接口曾因吞掉映射差异而带错数据，此后全组立规：要么对，要么报错。

保存后反查，把「写完必验」的验收闭环固化进迁移流程。

三、机械力：9 坑整理成清单

真实迁移路上踩过的坑，几乎全是「机械操作」层面的，值得原样记住。这 9 条全部是批量替换阶段的真实事故。

脚本与替换坑

  • 模块导入混淆：from . import X 被误转成 from .X import X。
  • 一次造成 20+ 处循环导入，对照源文件逐处区分同名导入。
  • 变量名被当成子模块路径解析、正则漏跨行：批量替换必须双人对照检查。
  • 脚本漏替换源目录：某区实例误迁进另一区文件。修脚本重跑加手工兜底。
  • 注释残留前缀（@Desc 等）导致对照脚本定位失败：手工修。

版本与平台坑

  • 子模块路径连字符 vs 下划线：版本体系依赖的坑。
  • .git/modules 需重建：版本体系依赖的坑。
  • 注册表缺括号：平台注册项机械错误，靠清单核对兜住。
  • create 与 edit 的 payload 模板不可互套，批量替换拿错模板必错。
  • pageType、queryString、batchid 在两操作间不同，对照 HAR 校验。

这些坑单个看都很蠢，共同点是：批量替换是盲目的，只有逐字段对比校验是有视力的。所以流程补上「完成后逐字段对比」这最后一步，才敢说迁完。

四、公共层：消灭重复才叫体系

迁移以「拷贝」开局是必然的（快速对齐现有实例），但拷贝必须收敛。收敛分三层。

第一层，公共基础包。五个组件收敛成一个只读引用源，多个实例统一引用，消灭重复：

  • 数据访问、协议封装。
  • 工具、日志、消息推送。

第二层，清洗逻辑公共库。各实例同源但微异的清洗逻辑，如诊断文本拆分、日期边界、身份证校验，收敛成公共模块。差异用开关配置区分，不复制代码。这就是「消除版本漂移」的正解。

第三层，版本子模块加固定提交顺序。公共包作为 git 子模块被多个项目引用，因此有了强制顺序：先推子模块，再推父项目。否则父项目指向不存在的 commit。

再往上一层，是面向「多个实例」的元工具：统一构建 CLI。一条命令遍历所有实例，做三件事：

  • 版本号管理：patch、minor、major 三档，本地与远程对比。
  • 构建前安全检查：拦截未提交文件、敏感文件保护。
  • 日志轮转。

到这一步，「迁移」才算结束，「运营一个体系」才开始。

五、AI 属性：先立约束再谈产能

前几章没有挑明的事实：这场迁移的主力是 AI 编程工具，不是人手。1:1 等价迁移规范、编码映射逐字保留、踩坑清单——这些纪律如果只对着人讲，就讲窄了；它们真正的对象是 AI。

  • 多 Agent 并行调研与独立审查：迁移路径由多个 Agent 并行起草，再由独立审查核对行为等价。
  • 审查是纪律的一部分，不是事后补救。
  • 1:1 等价规范是给 AI 的行为约束：禁止重构、编码映射逐字保留、宁多勿少。行为等价，才可自动验证。
  • 踩坑清单就是给 AI 的提示词：9 条坑全部是批量替换阶段的真实事故，固化成清单后成为验收的固定环节。
  • 规模与版本：Python 3.7 → 3.12 全面升级，覆盖存量全部业务线；行数与实例数一律隐去。

AI 在这里不是「写得更快的加速器」，而是被纪律化之后的工程产能。AI 越强，约束越要先立——这正是工程化方法论者对 AI 的态度。

写在最后：迁移工程的本质

回头看，这套方法论没有一条是「RPA 专属」的，它们全部是对不确定性的显式化。

  • 事实源是什么 → 用 HAR/协议锁定，不猜。
  • 结果对不对 → 保存后反查，用中文直比。
  • 失败怎么处理 → 快失败、必报错，绝不静默。
  • 谁改了公共的东西 → 子模块记录 + CLI 管版本 + 提交顺序立规矩。
  • 教训怎么留 → 每一条内联进规范，并注明它来自哪个实例、哪个教训。

把「搬文件」变成「搬确定性」，迁移就不再是冒险，而是可验收、可追溯、可复用的工程。这套打法，换任何一套技术栈都成立。
