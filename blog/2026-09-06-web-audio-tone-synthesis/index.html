Web Audio 起手式：从 oscillator 到音色

2026-09-06·Web Audio API音效工程纪律

这个站的按钮声、导航声、打地鼠的闷响，全部是代码算出来的，没有任何音频文件。

本篇分 4 部分。先讲清为什么走合成路线；再拆一条音从 oscillator 到包络的最短链路。然后处理打击音与浏览器自动播放这两个坑，最后讲音效多了以后怎么收敛成一张映射表。

一、零音频文件：一个架构选择

给站点加音效，直觉是找几个 wav 文件挂上去。真做起来先撞上三件事：素材要授权、文件要加载、音色不一致。

素材授权是最麻烦的一条。免费音效库里能商用的不多，要核对许可、要留出处；十几条音效逐个核对，成本超过自己合成。文件加载则是老问题：每个音频文件都是一次请求，一条 8KB 的点击声也要走一遍 HTTP。

第三条更隐蔽。从三个来源凑来的音效，混在一起会明显不搭：一个像游戏机，一个像系统提示。自己合成则天然统一，因为所有音都出自同一组参数。

所以本站的选择是 Web Audio API 程序化合成：音色由四个数决定——频率、时长、音量、波形。零文件零请求，代价是要自己写几条音。

二、最短的一条音：振荡器加包络

一条音的最小构成只有两个节点。振荡器（oscillator）产生波形，增益节点（gain）控制音量随时间的变化。

const osc = ctx.createOscillator();
const gain = ctx.createGain();
osc.type = 'square';
osc.frequency.value = 880;
gain.gain.setValueAtTime(0.045, t0);
gain.gain.exponentialRampToValueAtTime(0.0001, t0 + 0.08);
osc.connect(gain);
gain.connect(ctx.destination);
osc.start(t0);
osc.stop(t0 + 0.08 + 0.05);

四个参数决定听感。type 是波形，方波（square）是 8-bit 音色的招牌，泛音多、听着「电子」；frequency 是音高；gain 曲线是包络，也就是音怎么起、怎么落。

最后一行 stop() 的时间比时长多留 0.05 秒，不是保险，是必须。浏览器对已停止的振荡器会立即丢弃，如果 stop() 卡在包络到达零点的那一刻，尾部会被削掉，听上去像被掐断。

三、包络用指数衰减，不用线性

包络通常有四个阶段（起音 / 衰减 / 保持 / 释音，ADSR）。本站的音都极短，80 毫秒以内，所以只保留「起音加衰减」两段。

关键参数是衰减曲线。线性衰减写起来最直观：音量从 0.045 匀速降到 0。可人耳对响度的感知是对数的。线性衰减听上去是「前一半几乎没变、后一半突然没了」，指数衰减才对。

代码里用 exponentialRampToValueAtTime，注意目标值不能写 0。指数曲线的数学下限趋近于零但取不到零，传 0 会直接抛错。惯例是写 0.0001，比任何设备的最小可闻声都低。

还有一个细节：起音不要用 ramp，用 setValueAtTime 瞬时置位。方波本来就是硬边音色，加一段起音淡入反而变糊。

四、打击音：噪声缓冲

方波家族能覆盖点击、开关、导航，但这些音都有明确音高。打地鼠那一下的闷响如果也用方波，会像按了个键，不像敲了一下。

打击音需要的是噪声。OscillatorType 里没有噪声，得自己造一个缓冲：

const len = Math.floor(ctx.sampleRate * dur);
const buf = ctx.createBuffer(1, len, ctx.sampleRate);
const data = buf.getChannelData(0);
for (let i = 0; i < len; i++) data[i] = Math.random() * 2 - 1;

逐样本填随机数就得到白噪声，再用 createBufferSource 播放。整段噪声持续 80 毫秒，包络同样是指数衰减。

这就是 Game Boy 声音硬件的路子：两个方波声道加一个噪声声道（noise channel）专管打击乐。噪声不是「不够好听的妥协」，它本来就是那台机器的声音。

顺带一个成本事实。噪声缓冲是每次播放时现算的，80 毫秒加 44100 采样率是 3528 个样本，一次循环的耗时可以忽略。换来的是零文件依赖。

五、浏览器不给自动播：resume 的时机

音频代码在本地跑通、上线后没声音，多半是自动播放策略（autoplay policy）。浏览器不允许页面在用户交互前发声，这是防广告噪音的默认行为。

绕不过去，只能等用户手势。做法是在每次发声前检查状态：

if (ctx.state === 'suspended') void ctx.resume();

这里有个容易踩的细节：resume() 返回 Promise，不能等它。等它就意味着当前这次发声一定赶不上——手势回调同步执行完，声音才可能开始，而浏览器绑定的是那一次手势的授权。正确顺序是先 resume() 让上下文在后台恢复，同时照常排布这次发声，下一次点击就正常了。

另一个细节是 AudioContext 要复用，不能每次发声都新建。浏览器对同时存在的上下文数量有限制，几十次点击就会开始抛异常。所以上下文做单例，首次使用时创建。

六、从散装调用到角色映射表

音效只有三四个的时候，最容易的写法是每个组件各写一份。按钮里写 playClick()、导航里写 playNav()，看上去清楚。

这个写法会烂在一次疏忽上。加一个新按钮时忘了挂音效，页面不会报错，只是没声音。这种遗漏没有任何机制拦得住——它只能靠人记住。

收敛办法是把音效抽成数据。本站定义六个角色：导航、点击、开关、选择、游戏、悬停。每个角色对应一组合成节点：

export const SOUND_ROLES: Record<SfxRole, SoundSpec> = {
  nav: {
    nodes: [
      { wave: 'square', freq: 660, dur: 0.07, vol: 0.03 },
      { wave: 'square', freq: 990, dur: 0.07, vol: 0.03, delay: 0.07 },
    ],
    fx: 'nav',
  },
  // ...
};

角色表是纯数据，于是可以单测：角色是否齐全、参数是否在合法区间、页面里用到的角色值是否都在表内。加新按钮时，只要标上 data-sfx-role，接线是全站一次委托完成的。

有了角色表，音色调整也变了性质。原来调音要改十几个组件，现在改表里一个数。这是同一件事的两种成本，选哪个不用犹豫。

七、这套做法的边界

合成路线不是万能的，说清楚它什么时候不灵。

需要人声、需要真实乐器、需要环境音，这些合成做不出来，也不该硬做。那种场景老老实实用素材文件，把授权理清楚更省事。

音效数量上到几十条以后，手工维护参数表会失控，需要一套音色设计方案（采样率、音阶、音色分组）。本站只有六条，还没到那个问题。

最后一条边界最重要：音效默认开着、且每次导航都响，会烦。所以开关必须显式存在并记住用户选择。加音效是一秒的事，加一个能关掉的开关才是完整方案。

声音是页面的第四通道，前三个是布局、颜色、动效。它的特点是用户不会盯着看，但关了会立刻觉得空——这种感知上的默认值，值得用代码合成一遍。
