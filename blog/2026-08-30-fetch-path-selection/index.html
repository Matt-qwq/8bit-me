取数别默认点 UI：五条路径的选型纪律

2026-08-30·Python数据管道取数方法论

接到取数需求，最顺手的直觉是让脚本替你去点页面：点按钮、翻页、等表格渲染完再抓。那是把脚本当成人工替身，也是取数路径里最贵的一种写法。方向应该反过来：先找数据通道，再决定要不要碰页面。

页面很少自己生产数据。后台页面大多先用接口把数据拉回来，再渲染成表格，渲染只是给数据穿的一层衣服。脚本绕开接口、去衣服堆里抠数据，等于放着最近的路不走。

本篇分 5 部分。先立靶：为什么默认不该点 UI，以及像人者靠前的排序轴。再逐条过五条路径的适用与代价。后两节讲共享层收敛一处，末段划边界回扣。

五条路径按「越像真实用户越靠前」排开：

选型轴：越像真实用户，越靠前

1　页面内 fetch
　cookie 自动带齐 · 字段完整
　数据在页面接口里

2　UI 页面驱动
　拦截响应 · 流量与埋点真实
　数据在操作流程之后

3　报表导出下载
　服务端口径 · 文件头定格式
　页面留着官方导出

4　DOM 表格兜底
　滚进视口轮询 · 最慢最脆
　只剩渲染出的表格

5　重放式历史引擎（已退场）
　requests + HAR · 快但不像人
　拼请求 + HAR 回放

前四条现役，共用同一层地基：真实浏览器内核与会话。

一、为什么默认不该点 UI

点 UI 的代价，结算在每一次运行里。脚本要等页面加载、等按钮可点、等表格出现，任何一处超时，整条流程就断。页面结构一改，等待序列就失效，脚本要么报错，要么静默抓错数据。

更要紧的是，点 UI 拿到的是渲染结果，不是数据本身。表格往往只是接口的一个子集：分页会截断，列会被裁掉，虚拟滚动只画出看得见的行。页面背后那条接口，才是完整数据的家。

页面是入口，不是数据本体。顺序反了，脚本就把最贵的路走成了默认——取数的第一个决定，不该是点哪里，而是走哪条道。

二、排序轴：像人者靠前

五条路径的排序轴只有一条：越像真实用户，越靠前。平台会留意不像人的流量，也会埋点画像；像人的请求最不容易被单独挑出来。像人往往也更稳：请求从页面语境里发出，cookie 与上下文自动带齐，不依赖页面长相。

但能不能走最像人的那条，不由偏好决定，由数据形态决定。同一份数据，有的页面把它放在接口里，有的藏在操作流程之后，有的只以导出文件或渲染表格露面。判据是两个问题：数据以什么形态存在，哪条路离真实用户最近。

三、五条路径的适用与代价

五条路径按轴排开，形态各不相同。前两条是页面自己的通道，第三条已退场，后两条在文件层与渲染层兜底。逐条看适用与代价。

页面内 fetch

页面内 fetch 是五条里最接近人工浏览的一条。在页面上下文里执行 evaluate 发请求，cookie 与请求头自动携带。请求从页面语境里诞生，本质上是页面自己的请求。

它不点任何控件，页面改版不碰脚本；取回的是接口原始 JSON，字段完整、即取即验。前提是页面存在这条接口，且浏览器带着登录态——多数后台页面满足，所以它能覆盖最大一批需求。

# 伪代码：在页面里直接取页面自己的接口
data = page.evaluate("fetch('/api/report/list').then(r => r.json())")

UI 页面驱动

当数据只出现在操作流程之后，fetch 就没有落点。多步操作、提交动作、带会话令牌的请求，都得真实点击。配合 page.on('response') 拦截响应，页面收到什么，脚本就同步拿到什么。

代价是慢与脆：每次都要走完整段流程，页面结构一变就可能断。可它的流量与埋点都是真的，仍是第二近的路径。它不是默认项，而是 fetch 兜不住流程时的正解。

重放式历史引擎

第三条路属于过去。它用 requests 直接拼请求，再用 HAR（HTTP Archive，真实流量记录）抓包回放。它快，不起浏览器、请求拼好即发；可快的只是发得出去，不是像真人。

回放的是浏览器过去的流量，会话凭证过期就断；连接也已脱离真实浏览器，这正是它被真实浏览器取代的原因。重放没有未来，它留在清单里，是提醒后来者为什么不用它。

报表导出下载

有些页面难找接口、又不宜逐页翻，却留着官方的导出按钮。走导出下载，拿到的是服务端按官方口径生成的文件，大批数据一次拿完；对这类报表页面，它往往才是首选。

工程代价在文件层：下载常不带后缀，要按文件头魔数定格式。OLE2（复合文档格式）是旧版 Excel，xlsx 是 ZIP 容器，读头几个字节即可分辨。报表还常是两级表头，大类下再分细列，入库前要先合并成一行。

DOM 表格兜底

接口封死、又无导出的页面，最后只剩渲染出来的表格。这时抓 DOM（文档对象模型）：读可见表格行，把行结构转成数据。

虚拟滚动表只渲染视口内的行，直接读永远读不全。要把行滚进视口，再按行数轮询，行数连续几次不增长，才算抓完。

它是五条里最慢、最贴页面结构的一条，最该放在最后。前四条都判死刑，才轮到它上场。

路径会选，只是选对了门。四条现役路径长在同一栋楼里——同一个真实浏览器内核。这栋楼若每个工具各盖一座，路径再齐也是散沙。

四、共享层收敛到一处

现役路径共享同一层地基，这一层只实现一遍，所有工具复用。地基管的是各条路径自己管不好的事：

  • CDP（Chrome DevTools Protocol，浏览器调试协议）连接真实 Chrome；
  • 独立 profile 副本持久化登录态，会话不散在各工具里；
  • WS（WebSocket）僵死自愈，连接断了自动重建；
  • iframe（登录框与业务页）与 XPath（XML 路径语言）统一处理；
  • 文本选取 normalize-space 优先、id 兜底。

所以还有一条硬约束：浏览器启动后不许关闭。关一次，登录态与上下文就清零，之前的铺垫全作废。铁律护的不是进程，是会话的连续性。

这些事的共同点，是它们决定工具在平台上像不像一个稳定的浏览器。登录态、连接与定位这些地基，任何一件各写各的都会各自走样。有的补了、有的没补，平台看到的就不是一个真人，而是一群步调不一的机器人。工具不重复实现，收敛是为了让所有路径对平台呈现一致的长相。

收敛的第二个理由在维护。登录过期、浏览器升级、页面改版，都只改共享层这一处；加一条新路径，等于在新数据形态上复用老地基。地基越厚，路径越薄，这才是「能跑」与「成体系」的分界。

五、边界：路径选对只是半程

边界要先说清：路径选对，只解决从哪拿。取数还有另一半——过程要稳、结果要验，得靠登录态与校验那套守住；路径只是其中一环。

五条路径也不是每页都齐。有的页面只有导出可用，有的只剩 DOM；走哪条，仍由数据形态与真实用户的距离决定，不该让顺不顺手替像不像人做主。

回到开头那句「先找数据通道」。通道在前，页面在后；页面是最后一扇门，不该是第一选择。顺序对了，取数才算从手艺活变成工程活。
