三层风控：先证你是谁

2026-08-31·Python反爬风控方法论

抓取与反抓取的对抗，容易被想成一堵墙：撞上去，被弹回来。现实里的反爬很少是一堵墙，更像层层递进的关卡，每道关问一个不同的问题。

这篇写给采集端自己：先把目标端的三层关拆开，再逐层定我们的请求与校验怎么配。目标端常设三道关：L1 出身关、L2 行为关、L3 算法关。三层想验证的东西完全不同，混着打，力气就会花错地方。

本篇分 5 部分：反爬为何分三层、出身关先验什么、行为关怎么判、算法关为何专盯少数、校验为何收口在数据保真。

三道关是一条漏斗，越贵的分析越靠后：

三道关 · 越贵的分析越靠后

请求 REQUEST
　页面自身语境发出的会话
　↓
L1 出身关
　cookie · CSRF · token 一致
　↓ 页面外拼装的请求 → 拦下

L2 行为关
　IP 限频 · 节奏序列 · 蜜罐
　↓ 拒绝 · 限频 · 弹验证（显性）

L3 算法关
　实时打分 · 轨迹建模
　↓ 降权 · 延迟 · 静默分流（隐性）

放行 RELEASE
　出身与行为自洽 = 像人

多数脚本在前两关就露馅，能漏到 L3 的只是少数。

一、反爬为什么分三层

反爬分三层，首先是成本使然。L1 只比对 cookie 与令牌，最便宜，放在最前面。L2 要做统计与建模，贵一些，放在中间。算法层的深查最贵，只留给躲过前两层的少数。

三层还是漏斗式递进：出身不过，请求到不了行为层；行为可疑，才可能被算法层盯上。前一层合格，后一层才细看；越贵的分析越靠后，只留给少数。若把三层合成一道，要么贵得连真人都误伤，要么松得漏掉脚本。

出身关具体验什么，token 又为什么非对上不可？

二、L1：先证请求出身

L1 验的是请求出身：请求是否来自真实登录、且由页面自身语境发出的会话。cookie 确认会话存在且新鲜；CSRF 令牌（跨站请求伪造）防请求被别的页面借走。出身正当只说明请求来自页面语境，并不区分操作者是真人还是脚本。

出身凭证是 token 与 cookie 一致：请求体里的 token，要和 cookie 里内嵌的对得上。cookie 会被浏览器自动带上，第三方页面也能借它发请求，却读不到 cookie 里的值。只有从页面自身语境发出的请求，才能把同一个 token 带进请求体。

出身关，脚本驱动页面也能过，它证明不了操作者是人。它真正卡的是页面外拼装的请求，这正是「先证你是谁」排第一的原因：出身不正，后面两层的行为证据都无从谈起。真人还是脚本，留给 L2 与 L3 去判。

三、L2：证明你像人

出身证明不了操作的是不是脚本，L2 才转向行为。行为关盯统计：单个请求可能全部合法，但整段轨迹的分布可疑。IP 限频约束总量，是最粗的一档，同一来源的请求不该超过一个人的物理可能。它不逐请求定罪，而是攒够一段轨迹才下结论。

更细的判据在节奏与序列：请求间隔的分布、页面跳转的顺序、埋点画像，都在回答同一件事。这段轨迹像一个拿着鼠标的人，还是一台匀速的机器。

蜜罐（honeypot，抓爬虫诱饵）属 L2 便宜陷阱：页面里埋真人看不见的链接或字段，脚本扫过去就露馅。行为关的裁决可轻可重：显性的是拒绝、限频、弹验证，静默的是降权、延迟。实时打分把轨迹喂进模型，低分会话被静默分流，也属于这一档。

多数脚本在前两关就会露馅，能漏到算法层的只是少数。算法层要对付的，就是这批少数。

出身与行为都过了，剩下的少数怎么办？

四、L3：专盯漏网的少数

L3 是算法层，专盯躲过前两层规则的少数流量。它不对全量动刀：便宜的通用信号先铺底，可疑子集才上更贵的深查。多数请求到不了这里，重手段不值得铺在全量上。

真被算法层盯上，最阴的对抗手段是假数据投喂：只针对定向抓取者，成本高，不常用。它的失败是静默的：请求全成功，页面全正常，只有数据错了。

拒绝与降权都发生在请求侧，还能看到痕迹；数据掺假发生在数据侧，请求侧看不出异常。假数据不会报错，却会顺着管道流进数仓，被当成干净事实继续使用。数据已错却看似正常的根源就在这一层；防线在数据侧，不在请求侧。

五、防御收口在数据保真

采集端的防御，为何要收口在数据保真？因为要守的不是不被拦，而是拿回来的数据是对的。出身与行为做得再好，也只保证请求顺利；若被喂了假数据，管道会照单全收。

对齐的落点是校验，且必须在采集侧做。抽样核对字段、同一数据多来源比对、观察数值分布是否突变，都是让静默错误显形的办法。校验成本远低于一批假数据入库后重做的成本。把成功当默认、校验当必须，是掐掉静默错误的最后一环。

三层风控，从请求出身一路编排到数据保真，前两层看清目标怎么筛，最后一层守拿回来的东西是真是假。先证明你是你，最后是为了证明数据是数据。
